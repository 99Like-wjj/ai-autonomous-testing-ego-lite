# 两阶段报告的语言、模型来源与展示优化方案

状态：方案已获批准并实施，本地工程及离线页面验证完成。实际验证范围见开发验证记录。

日期：2026-11-02。

依据：PRD042本次执行与报告复核、当前v9契约和报告实现，以及用户对两个阶段的确认。

## 1. 两个阶段与两个展示位置

| 阶段 | 交付 | 头部模型信息 |
| --- | --- | --- |
| 用例生成 | 用例报告，沿用HTML与Markdown同源交付 | 用例生成模型、思考等级 |
| 测试执行 | 一个测试报告，沿用HTML、JSON、Markdown同源交付；包含执行、判断和报告分析 | 测试执行阶段模型、思考等级 |

“执行判断”和“报告分析”都属于测试执行阶段，不增加独立阶段、第三份报告或第三处模型展示。测试报告头部只显示本阶段模型信息；使用的用例版本继续通过现有版本/来源入口查看。

阶段内若使用不同模型或不同思考等级，仍只在该报告的一处位置显示“多模型配置”，展开同一位置查看明细。不能将最后一次整理报告的模型当成整个阶段的统一模型。

## 2. 本轮项目优化范围

1. 用例报告和测试报告统一采用用户在本次任务中与AI交流的语言；用户明确指定输出语言时以指定为准。
2. 两份报告各增加一处具有来源的模型及思考等级展示。
3. 用例总览支持长场景编号，消除编号与场景标题重叠。
4. 报告范围文案区分首次执行、按编号执行以及有比较基准的回归。

本方案针对测试项目的能力与展示。既有业务目标、四态及AI自主选择方法的职责继续按现有架构处理。模型执行中的错误另行评估模型效果，不把这些错误全部转成固定业务执行规则。

## 3. 统一语言

### 3.1 拟加入Skill入口的总则

> 用例报告和测试报告的输出语言跟随用户在本次任务中与AI交流的语言；用户明确指定输出语言时，以指定为准。所有由AI撰写、面向读者的内容使用该语言，包括用例标题、前提、计划步骤、预期、观察、实际动作、判断理由、问题描述、影响、缺口、诊断、输入/回复摘要及报告阅读整理。报告标题、导航、按钮、状态名称及提示文案也采用同一语言。产品原文、对话原文、报错、代码、字段名和标识符按原样保留，需要解释时另用报告语言说明。保存用例、登记结果及交付报告时，核对当前提交内容的语言一致性。

AI依据本次任务的交流上下文确定输出语言，不以需求文档、被测网站、引用文字或示例的语言替代用户交流语言。混合语言交流时结合主要语言与用户意图判断；只有确实无法确定且影响交付时才澄清。用户要求切换输出语言后，后续交付采用新语言，既有原件保留。

这是当前Skill的一处通用要求。case-authoring、judgment-and-diagnosis和evidence-and-report引用同一总则，并补齐各自适用内容；不在每个测试步骤重复相同指令。

相关示例明确说明输出语言应随用户交流语言确定，不把示例自身使用的语言当作默认限制；代码标识、协议枚举及必须原样保留的外部内容保持其真实值。无需为语言统一引入额外模型调用。

### 3.2 工具职责

AI在写入前完成内容的语言整理，工具负责准确保存与展示。两类报告的展示参数记录选定的language；固定页面文案通过同一份语言文案映射提供，HTML的lang属性与所选语言一致。用例报告与测试报告共用通用文案，分别保留各自必要的页面文案。

语言文案映射支持本次选定语言，不把可用语言限定为中文或英文。没有现成文案时，由当前AI提供同结构的目标语言文案，工具核对必要键和占位符，并随交付保存；不静默回退成其他语言。固定文案与业务正文分别提供，但呈现时使用同一输出语言。JSON字段名、业务标识符及引用原文保留其真实值。

不使用某种语言的字符占比作为交付拒绝条件：合法报错、代码及对话原文可能使用其他语言。语言是否清楚、一致属于AI的内容核对；Schema继续检查类型、来源和引用。

已有记录如需按另一种语言展示，应另存事后阅读整理及新报告，并声明来源。翻译不能改变原判断、实际输入、操作对象或证据原文。

## 4. 模型及思考等级的来源设计

### 4.1 页面样式

用例报告标题下方：

以下为用户使用中文交流时的展示示例，固定文案随实际输出语言调整。

```text
用例生成模型：gpt-6-luna    思考等级：max    来源：宿主元数据
```

测试报告标题下方：

```text
测试执行模型：gpt-6-luna    思考等级：max    来源：宿主元数据
```

模型信息使用可复制的页面文本，跟随现有主题样式；窄屏允许换行。标题、模型信息、版本或Run信息有清楚的层次。

常见状态：

| 留存事实 | 头部展示 |
| --- | --- |
| 同阶段已留存资料只有一种已知配置 | 显示模型名与思考等级 |
| 同阶段有多种模型，或同一模型有多种思考等级 | 显示“多模型配置 · N种”，展开查看各配置及来源 |
| 模型已知，思考等级未知 | 模型名＋“思考等级：未记录” |
| 该阶段没有模型来源 | “模型：未记录；思考等级：未记录” |
| 部分贡献没有来源，其余贡献已知 | 显示已知配置，并提示“部分来源未记录” |

“报告分析”发生模型切换时，将其实际配置合并到测试执行阶段的同一明细中，不生成第三个阶段。仅重新运行本地渲染命令不产生新的AI贡献，也不自动加入当前调用者的模型。

### 4.2 统一数据结构

建议增加可选的aiContext，其内部使用配置列表。以下是概念字段，正式类型由Schema生成：

```text
aiContext
  uses[]
    model: string | null
    reasoningEffort: string | null
    sourceKind: host_metadata | user_statement | unknown
    source: 既有来源结构，保留定位、摘录、文件指纹和局限
    scope: 对当前用例版本、入账记录或阅读整理的简短适用说明
```

source标明信息怎样取得及可定位依据；已有文件来源时沿用文件指纹检查。模型和思考等级使用实际原值，不把模型名写死为某一供应商，也不预设所有宿主使用相同的等级枚举。

来源处理原则：

1. AI优先使用本次宿主明确提供的元数据；用户声明单独标注来源性质。
2. 未知字段使用null并显示“未记录”，不由模型自我猜测，也不根据当前界面选项回填历史。
3. 可保留仅含模型信息的最小来源副本及指纹；本地工具不自动扫描全部宿主会话。
4. 工具检查结构、文件及引用，不把一个sourceKind字段当成对宿主身份的独立认证。
5. 模型名、思考等级和实际测试质量分别呈现，不根据max或模型名自动给出“适合该难度”的结论。

阶段由所在资产决定，不在业务流程中增加第三个阶段：

| 保存位置 | 归属与作用 |
| --- | --- |
| 用例保存请求和已保存用例的aiContext | 用例生成阶段；用例报告直接读取当前版本的来源 |
| 实际RecordPayload的aiContext | 测试执行阶段；适用于该次实际观察、判断或整理贡献，串行和工作包采用同一结构 |
| report-context的aiContext | 测试执行阶段；用于AI确实提供了事后阅读整理的情况 |
| Report的模型展示投影 | 根据当前运行入账记录及本次report-context汇总，精确去重配置，保留来源和未知项 |

测试执行阶段的汇总不混入用例生成模型、历史父运行模型或仅负责本地文件渲染的工具。并行工作包保留实际工作者的来源，协调者不将其覆盖成自己的模型。

### 4.3 版本和历史影响

建议沿用当前v9增补可选字段的方式，定义统一aiContext并更新相应Schema、运行时解析、生成类型、工具修订和文档。缺失字段对应真实的“未记录”，不增加按旧版本猜测模型的分支。

新用例保存时将已知生成来源一起保管；用例文件发布后仍保持不可变。用例定义完全未改、save返回unchanged时，保留原生成来源，不能把当前模型替换为历史生成者。模型说明不进入业务目标的定义指纹，不触发未改目标的业务重新审阅。

原有文件保持原字节及指纹。为本轮历史报告补充已核实来源时，应通过明确指向原件的事后展示来源生成新文件，不直接编辑cases、results或旧报告。用例报告如需事后模型说明，可在文档生成入口接收只读的aiContext补充文件，并在页面标注“事后补充”；其适用的casesRef及来源指纹必须匹配。该补充不改用例定义或审阅确认。

旧工具对未知字段可能拒绝读取新增资产；实施后要说明需要使用配套工具修订。与本次能力无关的网络和对话独立契约不扩展。

## 5. 长编号布局

当前场景列表把编号放在48px的固定列中；真实编号所需宽度超过该列，覆盖了右侧中文标题。

建议场景总览改为以下列：

```text
展开 | 业务场景（场景标题＋下一行完整场景编号） | 用例数量 | 计划状态 | 评审意见
```

具体规则：

- 场景名称作为主要信息；现有场景ID在同一单元格下一行使用较小的等宽文字，名称及页面文案按所选语言展示。
- 完整ID允许在必要时换行、选中和复制，不另造编号，也不截断丢失原标识。
- 名称单元格允许收缩，长英文ID使用明确的换行规则；两行内容分别占据自己的排版空间。
- 表头、场景行、展开后的子用例列表和移动端布局同步调整；子用例仍保留原pointId。
- 筛选、展开、定位当前用例及评审意见暂存沿用现有交互。

## 6. 首次执行和回归的文案

当前HTML和Markdown直接将mode=full写成“全量回归”，没有考虑是否存在明确比较基准。

建议依据精确的primaryBaseline和选择模式生成统一的展示文案。下表为中文示例，实际通过所选语言的文案映射呈现：

| 范围条件 | 展示文案 |
| --- | --- |
| full，未指定主要比较基准 | 当前用例版本全范围执行 |
| full，有明确主要比较基准 | 全量回归（当前用例版本） |
| points，未指定主要比较基准 | 按编号执行 |
| points，有明确主要比较基准 | 按编号回归 |
| status，根据历史目标状态命中场景 | 按历史状态选择，命中场景整体重跑 |

原范围/选中/冻结数量继续展示，明确“全范围”指所选用例版本，不能解释为PRD已经全部覆盖或全部完成。

有父运行资料但没有主要比较基准时，不仅凭存在历史文件就标成具有比较基准的回归。事后阅读整理也不构成回归依据。

HTML和Markdown采用同一纯展示函数，JSON继续保留精确选择与历史引用事实；标签变化不改选择集合、业务四态或历史关系。

## 7. 修改位置

| 范围 | 主要入口 |
| --- | --- |
| 语言及模型来源说明 | Skill入口、case-authoring、judgment-and-diagnosis、evidence-and-report、host-compatibility及相应示例 |
| 输出语言及固定文案 | 两类报告的展示参数、同源页面数据、共享语言文案映射、HTML语言属性及Markdown文案 |
| 模型元数据 | common/cases/cases-save-request/results/report/report-context等相关Schema，生成类型及运行时校验 |
| 用例保存与来源 | core/case-versions、core/baseline、report/case-reader；文档生成/本机审阅入口传递同源元数据 |
| 执行入账及汇总 | core/records、通用payload解析、工作包传递和复核导入、报告投影与delivery |
| 两个页面头部 | report/case-reader-shell、review-ui/app、report/shell、report-ui/main及对应样式 |
| 编号布局 | review-ui/app的总览结构、report/case-reader-layout |
| 范围文案 | report共享展示函数、report/render、report-ui/main |
| 验证及说明 | 对应测试、asset-formats、architecture和变更说明 |

正式实现时先从Schema生成类型，不直接修改generated目录；运行分发清单按实际新增运行文件同步。设计文档不等于安装、分发或发布授权。

## 8. 验收要求

### 8.1 两处模型展示

- 用例报告只显示用例生成阶段的信息；测试报告只显示测试执行阶段的信息。
- 单一模型、模型不变但等级变化、多模型、部分未知、全部未知均能准确展示。
- 当前模型切换不改变已有生成来源；纯渲染不增加AI贡献。
- 串行和工作包保留实际来源；同一报告的HTML、JSON、Markdown配置和来源一致。
- 伪造或失配的文件指纹、错误casesRef、非法结构被拒绝；来源未记录可如实交付。

### 8.2 语言

- 分别以中文、英文和另一种语言与AI交流，核对新生成用例、结果说明、阅读整理及固定页面文案均跟随该语言；用户明确指定不同输出语言时采用指定语言。
- 混合语言、外文需求和外文被测页面不应使报告偏离用户选定的交流语言；缺少目标语言固定文案时不能静默回退。
- 同一份报告的HTML、Markdown及JSON中的人类阅读内容使用一致语言，HTML的lang属性匹配；产品报错和对话原文保持原样。
- 长报错、代码、标识符不会被语言字符规则拒绝或篡改。
- 不同语言整理前后业务四态、实际输入、对象及证据指纹保持一致；事后整理明确标注。

语言内容是否符合要求由实际AI产出核对；工程测试只能证明工具保留文本和引用，不声称已经验证模型语言遵循效果。

### 8.3 布局和范围文案

- 使用本次长场景ID及更长合成名称，在常见桌面、平板和手机宽度实际打开离线页面，保留截图核对；编号不覆盖名称，复制所得标识完整。
- 新头部换行后，固定导航、目录表头、筛选、展开、当前项定位和评审草稿仍正常。
- 无主要基准的首次full执行不出现“全量回归”；有明确基准及按状态选择时使用正确文案，HTML与Markdown一致。

## 9. 实施顺序

1. 完成语言要求和aiContext的保存、汇总、两处头部展示及来源验证。
2. 完成长编号布局和范围文案共享投影。
3. 按修改范围完成相关工程检查，核对typecheck、npm test、check:public和diff；再用合成资料实际打开两类离线报告验证展示。

本方案实施验收使用合成资料和离线页面，结果不能替代真实UAT或不同执行模型的效果验证。历史用例、原运行和原报告继续保留。
