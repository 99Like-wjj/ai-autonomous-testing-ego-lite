## 1. 目标与范围

建议集中处理查询负担、局部模块依赖和报告措辞。默认并发继续为 1，明确配置才使用更高上限；执行时机、批次、worker、补测、暂停与业务判断继续交给 AI。当前默认值和并发守卫已有实现，不在本轮重新设计。[VERIFY: src/execution/config.mts:12-28] [VERIFY: src/execution/ledger.mts:141-146]

不增加服务、数据库、自动调度、持久化缓存或浏览器代理；不增加固定业务流程。保留历史操作、证据、Space 保护、名额限制、幂等和导入复核，不通过删除台账或降低判断标准换取轻量。

## 3. A：默认短摘要，需要时再展开

建议 CLI 保留一个查询入口，增加三种视图；以下是拟议接口，当前尚不可用：

```text
node ABS_TOOL_ROOT/scripts/ego.mjs execution read --run-dir ABS_RUN
node ABS_TOOL_ROOT/scripts/ego.mjs execution read --run-dir ABS_RUN --view assignment --assignment-id ID
node ABS_TOOL_ROOT/scripts/ego.mjs execution read --run-dir ABS_RUN --view full
```

- 默认 `summary`：返回 run／baseline 身份、revision、配置上限、已知容量、名额占用、收敛状态、待导入／未完成计数，以及必要的活动／异常分派摘要。历史操作、完整 packet、已完成分派和长事件列表不展开。列表较大时明确显示总数与截断信息，不静默隐去问题。
- `assignment`：只返回该分派的身份、执行状态、默认 Space／偏差、相关交付位置、导入进度和必要提示；返回文件引用，不自动打开截图或展开所有历史证据内容。
- `full`：显式读取完整历史及严格校验结果，用于诊断和复核。完整台账始终保留，不做历史裁剪或自动压缩归档。
- 摘要使用明确的视图类型／版本，不伪装成完整 `ExecutionLedger`。保持现有内部完整读取函数的返回语义，CLI 依赖旧默认结构的脚本改用 `--view full`；同步调用指南与开发修订信息，不维护隐式双默认模式。

现有写请求已经返回 revision 等回执，AI 可直接使用它们构造下一次数据请求，不必每写一次都先读整份台账。若 revision 冲突，再按需读取并判断；工具不自动重试业务动作或分派下一例。原来的幂等与 revision 冲突拒绝继续保留。[VERIFY: src/execution/commands.mts:22-30] [VERIFY: src/execution/commands.mts:88-90]

先只改变查询投影，保留现有校验路径。这样可以单独测量输出减少的收益，不把“输出变短”等同于“磁盘读取减少”。

## 4. B：状态读取与完整性复核分开

第二步让 `summary`／`assignment` 使用轻量读取，`full`、写事务和正式检查继续走严格路径。轻量读取计划如下：

1. 复用现有短时锁与安全路径检查，读取一致 revision；锁忙时返回明确事实，由 AI 决定等待或再次查询。
2. 解析 manifest、核对冻结基线哈希，校验 execution 的结构、操作关联以及 run／case／baseline 身份；不遍历历史截图、创建回执和 packet 文件逐个重新计算哈希。已有基线与执行身份校验可复用。[VERIFY: src/execution/ledger.mts:111-115]
3. 返回 `evidenceIntegrity: not_checked` 等明确标记，以及未完成导入／恢复标记。它只报告当前台账记录，不证明证据未变，也不重新确认业务通过。
4. 轻量读取不执行 `recoverEvidence` 或补写台账；有待恢复项就明示，由 AI 选择后续工具。原写事务的恢复与完整校验保持原行为。

严格写入、导入、`check`、`report`、`verify-report` 的现有证据校验和拒绝条件不削弱。证据损坏时，轻量状态可供排查，但不能称为完整性通过；严格校验和提交仍应拒绝。

这一步不增加基于 mtime／文件大小的可信缓存，也不保存第二份状态索引。仍需读取和解析完整 execution JSON，所以不能承诺历史无限增长时查询恒定耗时；本版先减少证据文件读取及输出，是否需要索引留给后续实测。

CLI 仍执行已安装工具文件的完整性核对，这项固定成本不混同于历史证据读取，也不在此方案中取消。[VERIFY: src/scripts/ego.mts:72-74] [VERIFY: src/scripts/toolchain.mts:45-56]

## 5. C：只调整一个局部数据边界

建议新增小型 `core/baseline.mts`，承接用例解析与基线读取／验证函数，依赖通用文件和校验能力；不包含运行初始化、结果写入、worker、Space 或业务决策。

- `core/cases` 继续负责 init／start，调用该基础数据模块。
- `core/records`、封包及轻量查询直接复用基础数据模块，读取用例不再引入 start 的配置／初始化职责。
- 现有对外 CLI 与导出入口保持，内部 import 一并调整；不复制验证实现，不引入依赖注入容器、执行后端工厂或通用仓储层。现有统一导出入口可以保持原调用位置。[VERIFY: src/scripts/ego.mts:14-20]

只在实现 B 时配套做这个抽取，不为降低目录级双向依赖而单独发起大重构。原有证据／结果事务继续复用，避免维护两套存储规则。[VERIFY: src/execution/commit.mts:67-85]

## 6. D：修正记录措辞，避免替业务下结论

- 把“从未尝试”改为“尚无结果／尝试记录”，使其与实际统计条件一致。
- 把“已尝试但无最终结论”明确为“已有尝试记录，尚无最终结论”；已有执行面板继续显示 reserved／running／paused／completed 等状态。
- 不把 reserved 当作已经执行，不把 completed 当作业务通过，不修改 pass／fail／blocked／inconclusive／not_run 的存档记录，也不重新推断四态目标结论。当前目标结论取自关联的显式 AI 评估，保持这个来源规则。[VERIFY: src/report/execution-view.mts:4-14]
- 只影响今后生成的报告。旧 HTML、JSON、Markdown、截图与 UAT 冻结包不覆盖、不重新生成。

## 7. 实施顺序与验收

建议先 A＋D，测量证据读取成本后再决定 C＋B。第二步以实测存在明确收益为前提，收益不足时保留第一步、不扩大改动。两步各自形成可审查的小改动，完成前一步不代表后一步已有性能收益。

| 验收项 | 拟验证方式 |
| --- | --- |
| 查询输出 | 同一有效合成台账分别读取 summary／assignment／full；确认身份与 revision 一致，默认输出无完整历史 packet，单例不混入其他分派。 |
| 输出收益 | 用 100 用例、1000 历史操作的有效合成数据做前后对比；建议默认摘要相对旧全量输出至少减少 90%。该数值是待验证目标，不是现有结果。 |
| 证据读取 | 记录查询期间实际文件读取：轻量路径不读取历史证据 payload，严格路径仍读取并校验。基线与安装工具资源检查不计作历史证据读取。 |
| 性能记录 | 预先准备同一组合成数据，在相同 Node／硬件环境对比进程耗时、输出字节数、文件读取量与耗时中位数；构建与造数时间单列，不预先承诺固定倍数。 |
| 拒绝与恢复 | 错 run、坏基线、非法结构仍拒绝；改动／删除证据时轻量查询明确未查完整性，严格检查、写入和报告继续拒绝。中断导入显式提示，不由查询静默恢复。 |
| 并发安全 | 保留默认 1、显式 6／12、宿主未知／已知容量、在途保留名额、降低上限收敛、Space 所有权与幂等回归；摘要不成为跳过写入校验的通道。 |
| 报告准确性 | 覆盖仅 reserved、执行中但无入账观察、已有 attempt 无 final、completed 未导入和已有 final，以及 v3 旧运行。原业务记录不因措辞变化而改变。 |
| 模块与交付 | 严格类型检查、契约生成检查、依赖无环、完整离线回归、安装清单与独立包检查；如需看 HTML，只用新的合成报告。 |

实施与验证均限定在唯一源码目录及常规构建产物、私有合成验证资产内；保护本轮已有未提交修改，不新建源码备份或版本目录，不修改用户级已安装 Skill，不推送、打 Tag 或发布。真实 UAT 的恢复不包含在本方案中。
