## 结论与适用范围

原始实验中，新旧规则的 agent 都在 CHAIN-01 首个业务动作之前实际询问六类已知资源，且都正确处理纯设计、资源已齐备和提问传输失败三个边界。不能把本样本描述成“旧规则没有提前澄清、修复后才会澄清”。候选版可见的改进是首次执行前和部分答复后的范围摘要更明确、可追溯。

原始控制器存在两类影响分支覆盖的问题：合理的只读登录失败观察没有触发替换答复；附件依赖被提前暴露，但提前提出的问题又不能收到对应答复。另有文档自建/授权暂缓在同一 poll 同时送达的覆盖削弱。因此完整账号替换链尚不能判为已验证；候选版的具体对象删除确认链也未实际走完。不能宣称 A01–A14 全部验收完成。

审核对象是资源提问、实际受理、时机、事实承接、允许继续范围和恢复判断。合成业务目标的 verified/violation 数量不用于评价规则质量；这些模拟结果不代表真实 UI、Ego 或 UAT 的业务通过/缺陷结论。

审核者参与了题设与 rubric 设计，没有编写方案一产品规则或执行这些测试场景；是与执行者分离的审核，但不是独立第三方盲评。实际模型和宿主配置未写入模拟器事件，本文不猜测；交付时须与调度记录共同使用，不能仅凭这些日志声称控制了所有模型变量。

## 控制器污染及如何处理

1. **替换身份被固定动作路线限制。** `fixture.py` 第 35–43 行要求先出现 switch_identity/rejected，且问题必须晚于该动作。实际只读身份观察已经返回 rejected，合理路线会先问替代。原始实验 A06 完整链无法判断；需要在新 session 使用支持等价已知事实的控制器复核，不重写旧日志。
2. **附件依赖提前暴露、对应答案又被晚动作限制。** CHAIN-03 候选 e14 在 fetch 前读取到隐藏的附件权限缺口，e19 正确问此缺口，但 e20 fetch 后控制器要求新问题才能给 C3-R3。基线与候选由此没有经历等价的问答响应。旧 e20 已收到明确暂缓，新 e37 仍是已问待答，均是各自真实已交付事实；不能将差异解释为候选承接失败。
3. **同一次 poll 合并部分与最终答复。** CHAIN-02 两方初期都先核验外部授权，因此 C2-R3“可自建”与 C2-R4“本轮暂缓”同时交付。没有产生多轮部分答复间隙，A07 只能证明基本授权分离和暂缓边界，不能宣称这条完整多轮挑战已覆盖。
4. **按 goalId 关联答复，未自动理解题项语义。** 本次主要首问与答复的语义经过人工对照；控制器本身不能证明问答语义正确。C2 具体对象许可要求实际文本中出现已创建对象ID。阶段消息依据 report 次数触发，审核以实际消息/动作顺序为准，不把“消息已出现”直接等于恢复行为已验证。
5. **合成业务语义简化。** 删除对象后 `read_project/read_draft` 仍返回旧内容元数据；两方给出的模拟业务状态不完全相同。该差异不能作为本次资源澄清优劣或真实产品缺陷证据。CHAIN-01 普通成员负向设置许可的题干存在解释空间，新方额外问许可而旧方直接测试，不据此判旧方越权或新方更优。

### 基线补跑观察及剩余控制器限制

基线 v2 同样完成了失败身份替换、来源部分许可后的补问、具体删除许可和提醒恢复后的条件核对。不能将其全部描述为旧规则失败。

本次出现一个可确证的顺序差异：baseline-v2 / CHAIN-02 e7 已创建隔离项目，e10 才集中询问组织外身份、外部文档和删除条件；candidate-v2 e9 先完成这批提问，e13 才创建。两方创建动作本身均在已有授权范围内；差异是“恢复整轮测试前是否先沟通已知实质缺口”。基线这次没有满足新方案要求的前置时机，候选满足。原始实验基线却曾提前问到，因此这只支持一次具体行为差异，不能推出稳定改善率或所有旧会话都存在同样问题。
