## 1. 本期目标与判断口径

本期围绕首次设计、人工审阅、实际测试、问题复测及结果交付，提高测试目标的可追溯性、取证能力和报告可读性，并用实际对照检验测试效果及方案质量。

- AI 理解需求、设计目标与用例、自主选择方法并作业务判断；Ego 执行获授权的浏览器动作；本地代码处理结构校验、版本、引用、文件和报告等确定性事务。
- 用户指定的目标、预期、必要业务语义和授权保持不变。复用、缩小重测范围或恢复执行不能省略必要前提与读回。
- 业务目标继续分别使用 **已验证、发现违反、无法判断、未测试** 四态。审阅状态、执行状态、可比性、原问题复现情况和文件状态分别表达，不扩充或混淆业务四态。
- 点击、请求成功、文件出现、格式合法或报告完整都只证明相应观察；结论仍须核对业务预期。新发现与原目标结论分开留存。
- 人工审阅是本次明确增加的暂停环节，不据此固化测试探索、业务路线、重试策略或评分流程。

## 4. 逐项需求与验收标准

### R018-01：所有最小测试点具有稳定编号

编号单位是可独立判断的业务目标，覆盖成功、违反、无法判断与未测试的目标。现有 goal 是主要映射对象；步骤与动作不自动成为独立测试点。

- 编号在项目范围唯一、稳定、可读、可复制和可检索；跨运行保留同一业务目标的身份，不复用已退役编号表示其他目标。
- 身份与内容修订、运行、实际尝试分别记录，保留需求/规则版本、场景及原 caseId/goalId 映射。
- 目标语义改变、拆分、合并或退役时明确关系，不凭相同标题或文本相似度认定等价。
- 用例设计文档、执行记录、测试报告及比较结果都能使用编号定位。缺陷标识独立，同一测试点可关联多个问题。

验收：成功和失败目标都可唯一定位；跨两轮仍对应原目标；未知、重复和歧义编号明确返回问题，且不启动猜测出的测试范围。

### R018-02：按编号回测，区分原问题和新发现

- 用户提供一个或多个编号后，AI 可取得对应目标、当前用例/规则修订、必要前提、历史问题和关键证据，准备清晰的回测范围。
- 回测覆盖选中目标及其必要准备、身份、对象关系、必经路线和读回。辅助动作不自动形成其他目标的测试结论。
- 按编号回测、按状态选中整场景重跑、全量回归分别声明；保留既有整场景选择语义。
- 对原问题保存触发条件、问题步骤、预期、实际和证据，分别说明本次是否观察到原现象、目标是否满足要求、是否存在新问题。
- 保存已知部署、规则、身份、环境和数据差异；未知项标明未知。修复归因由 AI 依据明确事实说明，不从四态变化自动推断。

验收：仅给编号即可准备可审阅范围；依赖不遗漏，未选目标不继承历史通过；能够表达“原问题未再观察到，但目标因新问题仍发现违反”。

### R018-03：全量回归对照最新、完整、明确版本的目标清单

- AI 对照最新已确认需求核对目标清单，明确新增、变更、退役及尚未整理范围，并固定本轮采用的版本与来源。
- 全量不按历史成败、任务成熟度或资源就绪程度过滤。待补全、缺规则、缺任务、受阻、暂缓及缺评估项都保留位置与原因。
- 请求范围、选中范围、实际冻结范围和实际完成范围分别说明；既有旧测试集全选只代表该集合，不自动代表最新需求全覆盖。
- AI 可按依赖和共享状态安排执行，并说明影响检查依据；不擅自扩大真实业务写入范围或删减目标。

验收：新增需求不会因缺少旧执行记录被遗漏；缺任务、资源不足和暂缓仍可追溯；报告能够核对请求范围与实际完成范围的差异。

### R018-04：精确关联实际动作、结果和证据

- 关键实际动作保留身份、对象、必要输入、对应计划语义、实际结果、独立读回及支持的测试点，说明证据用途和局限。
- 精确引用支持该动作或判断的材料；共享证据标明共享及支持范围。没有逐步取证时保留缺口，不要求每次点击截图，不从计划补造执行经过。
- UI、接口、文件和其他观察按实际支持范围相互印证，保留首次异常、未知结果和处置事实。
- 报告突出问题描述、原预期及实际复现流程，能够直接进入问题步骤和证据；原始字段及历史折叠保留，减少重复铺陈。

验收：读者可从测试点定位实际问题步骤与相应材料；独立证据、共享材料和未关联材料可区分；展示整理不改写业务四态或首次现场。

### R018-05：参数化任务数据，保留本轮实际条件和必要关系

- 将可替换的角色、账号引用、项目/对象、日期和命名空间与业务预期分开；本轮实际值保留核验来源。
- 对象归属、前后置、历史关系、角色、版本和允许替换条件明确表达，不以空对象或高权限身份替代原必要条件。
- 保存可取得的被测环境、部署版本、模型/宿主/Ego 版本和数据初态；缺失项明确未知。历史可用及历史授权不自动成为本轮就绪依据。

验收：日期或对象变化无需改写业务标准；不等价替换能被明确识别并说明影响；比较可追溯每轮实际绑定，而非只看到参数占位符。

### R018-06：按需复用稳定操作片段

- 从实际需求中整理有复用价值的登录、导航、输入、截图和读回片段，记录适用条件、参数、实际回执及限制。
- AI 自主决定使用和组合方式；条件不符、页面变化、对象不唯一或结果未知时，片段返回事实，由 AI 决定下一步。
- 对有副作用的动作保留单次尝试的意图、发出、结果与对账；片段不内置业务自动重试、换对象、绕行或结论，不把探索脚本直接当作完整标准流程。

验收：复用能够保留必要业务语义与失败信息；关键结果仍有业务读回；未知副作用不会因片段复用而被自动重发。

### R018-07：开展测试效果对照与方案质量评估

- 采用脱敏或合成代表性需求、可核验预期、已知缺陷及正常对照，保留输入、实际输出、逐目标人工复核和证据位置。
- 分别分析需求覆盖、有效缺陷、误报/漏报、证据充分性、授权及数据安全和完成情况。仅在已知参考范围中讨论漏报，不编造未知缺陷全集或召回率。
- 对等目标与输入下记录改善、退化和波动，说明模型、宿主、浏览器、版本与环境条件。工程回归、合成演练、真实试跑和人工效果审核分别报告。
- 方案评审结合现有能力复用、职责划分、证据可靠性、必要依赖和可维护性说明取舍；不以新增工具或规则数量证明方案更好，也不固化业务判断或执行路线。

验收：对照结论能定位实际输出、原预期和人工判断；方案取舍有事实及验证依据；不依赖单一通过率、强制综合分或固定权重证明效果。

### R018-08：观察下载结果并检查实际文件内容

测试需要能够追踪页面操作触发的下载，判断是否完成，取得对应实际文件，并按用例继续检查数据。页面看见下载与 AI 未取得下载观察可能同时发生，须区分产品结果与观察能力缺口。

- 在当前实际安装版本上调研并验证普通链接、新页面、临时页面、浏览器生成文件和异步导出等实际相关路径；记录 UI 触发、浏览器生命周期、下载完成及文件访问之间的关系。
- 明确可支持的场景、实际取得文件的方法和已验证限制。历史监听超时不作为当前能力结论；仅完成调研不能宣称已交付下载验证能力。
- 将本次动作、来源页面、实际下载、文件名和文件身份准确关联，防止同名旧文件、并发文件或其他测试文件混入。
- 分别记录下载发起、完成或失败观察、文件是否取得、能否读取及内容检查结果。文件大小和指纹可支持身份/完整性核对，不单独证明业务数据正确。
- 内容检查依据原业务预期，例如字段、记录数量、筛选范围、权限范围及具体数据。详细设计明确首批格式支持范围和读取限制。
- 保留原下载入口和必要业务语义。只获取接口响应或另行请求同一资源，不能替代用例要求的页面下载完成验证。
- 未获得观察时保留真实缺口，由 AI 结合事实判断目标四态；不将监听超时自动归为产品失败，也不将 HTTP 成功或页面提示当作文件落盘与内容正确的证明。

验收：在当前安装环境中，选定的代表性业务下载场景能够完成“页面触发—确认下载—取得本次文件—读取并检查内容”的完整链路；成功、实际失败、观察缺失、同名文件和内容不符能够区分。临时新页等受限场景逐项报告结果和限制。若宿主能力不足以满足目标，应带实际证据说明缺口及范围影响，不能自行降低需求或把调研完成等同功能完成。

### R018-09：在报告中呈现复测历史和结果对照

- 首次测试没有先前轮次时，提供完整、纯净的正常报告，不显示空历史或无意义的版本对比。原始尝试留痕仍按事实保留。
- 后续复测在报告中连贯展示首次结果、历次实际复测和当前结果，支持查看相应预期、实际表现、问题步骤及各轮证据。
- 使用稳定测试点身份和明确来源关联历史；测试轮次、用例修订、软件部署版本和报告重生成分别表达。只补充说明、修订判断或重渲染报告不新增一次实际复测。
- 目标状态变化、原问题复现、新问题、可比性和修复归因分别展示。同一目标持续违反不必然是同一 Bug；违反转为已验证也需本轮事实支持。
- 已知规则、数据、角色、环境及部署差异就地提示；规则实质变化或目标拆分合并时保留映射与限制。
- 原运行、原报告、原证据继续保留；新报告的当前结论使用本轮事实，历史材料明确归属，不能冒充本轮采集。
- 部分重测分别展示本次范围和历史范围。未选中项若作为历史上下文出现，应明确本次未重测，不计入本次四态分布或已验证数量；本次选中但未执行的目标按事实记录未测试。
- HTML 侧重历史浏览与前后证据对照，Markdown 和 JSON 保留相同关联、状态、范围和关键差异。

验收：以“首轮违反、证据不足；次轮部分修复、部分仍不足；后续又出现新问题”的样例，能够逐点还原每轮结果与依据，并区分实际复测和记录修订。开发人员可以直接回答最初问题、本次怎么复测、原现象是否仍存在以及证据位置。

### R018-10：交付可视化用例文档并暂停人工审阅

- AI 生成测试点及可审阅用例草案后，默认暂停进入人工审阅。当前任务只要求测试点时，在测试点交付后暂停；要求完整用例时，交付足以评审的前提、必要操作语义和预期，不将评审拖到实际执行之后。
- 同一份结构化设计资产生成 HTML 与 Markdown。文档包含需求来源、模块/场景、稳定编号、业务目标、预期、必要步骤与依赖、测试数据要求、覆盖关系及待确认项。
- HTML 提供清楚的目录导航、检索、筛选和展开详情，适合分享与团队内部评审；缺口和假设可见，文档不以展示完整掩盖设计未确认。
- 保存审阅意见、受影响目标、AI 修改说明和人工确认的版本/范围，并能查看修订差异。评审记录只表达实际收到的意见与确认，不凭生成成功自动标为已审阅。
- 人工明确确认相应版本与范围后，才进入依赖该设计的测试执行；执行基线可追溯该版本。新增或实质修改内容应再审阅受影响部分，历史确认不自动覆盖新语义。
- 已确认且未实质修改的用例可在后续重测复用，保留本次范围和条件核对，不要求每轮重新生成整套用例；暂停审阅的范围不得被静默绕过。
- 已知的资源或判据缺口应及时沟通，不等待用例全部完成或评审结束才提出；设计中保留待补内容，实际执行前仍核对整轮已知条件与允许继续范围。
- 纯设计和审阅无需创建执行 run，不生成业务四态结果。设计确认、资源就绪和真实环境操作授权分别成立。

固定代码与 AI 的职责分工：

| 固定代码适合负责 | AI 与人工负责 |
| --- | --- |
| 资产结构、编号和引用校验 | AI 理解来源、设计目标、预期与必要语义 |
| HTML/Markdown 同源生成、导航和筛选 | 人工核对覆盖、业务标准及用例合理性 |
| 内容修订、差异、审阅意见和处理记录 | AI 解释并落实意见，说明未解决问题 |
| 实际确认记录与版本/范围绑定、冻结一致性核对 | 人工明确确认；AI 按授权规划执行与判断 |

验收：团队无需阅读内部 JSON 即可完成评审；能记录修改意见、查看修订并明确确认版本；确认前不进入相应测试执行；执行内容与确认版本可核对。HTML/Markdown 内容一致，且没有用虚假运行伪装审阅进度。

### R018-11：改善需求映射、覆盖与测试设计质量

- 将原始需求及其修订映射到场景和可独立判断目标，保留来源位置、明确要求、待确认解释与探索假设的区别。
- 针对相关业务要求检查正常、边界、异常、权限、状态和依赖覆盖，不为套满方法或增加数量机械扩充用例。
- 每个预期有来源，每个目标有适用前提、必要语义和可观察结果；拆分与合并不丢失连续流程依赖。
- 未覆盖要求、待澄清标准、资源缺口和明确不在本期的范围有位置可查；不从现有 UI、样例数据或模型信心补造验收要求。

- 针对实际暴露的误判、下载观察、复测对照、前提遗漏和恢复问题，核对设计经验及执行经验的适用阶段、前提、观察价值和限制。
- 补充确有复用价值的通用指导及反例，避免将账号、页面路径、项目规则或个别成功脚本固化为通用业务流程。
- 经验经人工语义审核后维护并随版本分发，普通测试运行继续只读；本期不增加运行时自动学习、候选经验池或强制逐例经验引用。
- 经验适用性和效果通过实际输出及受控对照核对，模型升级或指南变长都不能作为效果改善的依据。

验收：新增或修改条目能说明来源问题、适用条件和局限；设计/执行阶段引用无冲突；普通运行不回写经验；验证同时保留改进和仍存在的失败。
