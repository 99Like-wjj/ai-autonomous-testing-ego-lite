# v0.1.8 最终设计方案（收敛版）

日期：2026-11-01。状态：**最终设计已获用户确认，已进入 0.1.8-rc.1 开发与自测；当前核验见开发记录**。

依据：[已确认需求](v0.1.8-requirements.md)、[可行性调研](v0.1.8-feasibility-research.md)。本稿替代上一稿的通用项目资产库方案，保留全部 12 项需求。token、费用、用量和节省比例不在范围内。

配套：[轻量数据与接口](v0.1.8-contract-design.md)、[下载与文件检查](v0.1.8-download-design.md)。三份文档是同一最终设计，不是三个独立系统。该设计已用于当前开发候选；0.1.7 正式版不具备这些新增能力。实现与核验范围见[开发自测](v0.1.8-development-validation.md)。

## 1. 收敛后的核心

只保留三类需要长期保存的内容：**用例版本、审阅依据、历次运行**。一个测试工作目录可以持续使用；不会每轮重建项目、复制全部需求或重新整理所有资料。

| 内容 | 保存什么 | 什么时候新增 |
| --- | --- | --- |
| 用例版本 | 场景、测试点编号、预期、必要步骤、来源与参数要求 | 首次设计或定义确实发生变化 |
| 审阅依据 | 对具体用例版本及目标范围的实际意见或确认 | 实际收到评审意见或确认 |
| 本轮运行 | 使用的基线、选择范围、当前条件、动作、结论、证据与报告 | 每轮实际测试或复测 |

规则直接作为用例的依据与预期，任务直接作为场景的前提和步骤，问题留在运行中的 findings/评估记录。不再创建独立 point/design/rule/task/issue 修订库，不增加通用 asset 管理接口、项目运行索引或资产版本体系。

设计确认时基线为 0.1.7 / v8 / regressionVersion 1。当前源码候选为 **0.1.8-rc.1 / case-review-native-export-1、主契约 v9、regressionVersion 2、networkVersion 1**，旧资料保持原样。后续获准的总览/三栏评审和本机文件保存修复见[审阅说明](v0.1.8-case-review.md)，不改变用例定义或实际人工确认要求。

## 2. 测试资料目录

这里的工作目录是用户选定的测试资料位置，通常在通用 Skill 和源码仓库之外；不要求在被测应用源码中建立库。

```text
<测试工作目录>/
  cases/
    v001.json
    v001.html
    v001.md
    v001-review-01.json
    v002.json                  # 定义有变化才新增
  runs/
    run-001/
      manifest.json / baseline.json / run-binding.json
      results.json / evidence.json / execution.json
      evidence/ / workers/
      report.html / report.md / report.json
    run-002/
```

JSON 是结构化用例原件；HTML/Markdown 是同源生成的阅读文档。展示重生成可以另选输出位置，不产生新的用例定义版本。只有实际存在的记录才创建相应文件，纯设计不创建运行。

编号分配、并发写保护和重复写入恢复复用现有文件事务能力，作为内部实现；不建立 allocations、operations、reviews、assets 等项目级分类目录。用例文件自身保存所需的版本、编号计数和写入指纹。

## 3. 用例版本与稳定编号

### 3.1 保留现有场景结构

用例继续采用 cases→goals，每个 goal 增加稳定 pointId；原 caseId、goalId 继续用于本轮局部定位。一个用例版本包含相关场景与目标，不为每个测试点创建独立文件。

目标继续保存依据、预期、必要引用和待确认问题。条件改为带稳定 ID 的对象；步骤可声明 dependsOn。沿用 requiredRefs 表达必要条件、步骤和必经路径，不增加独立义务对象或通用依赖引擎。

定义尚不完整的目标标明 planState=unprepared 及具体缺口，可以没有完整步骤映射；已知要求仍保留。planState 只表达设计是否可执行，当前账号/数据等资源是否就绪另记在本轮条件中，不因此每轮修改用例。

### 3.2 编号在同一次保存中分配

用例文件内嵌 projectId、pointPrefix、nextPointNumber 和已退役编号。编号例如 SAMPLE-TP-000001，覆盖全部四态，不只给 Bug 编号。

新增目标在保存请求中使用临时局部 ID 和空 pointId。工具在 cases 目录锁下读取前版，在内存分配编号，并把完整新版本一次性无覆盖发布；成功后才返回正式编号映射。不提前对外公布未提交编号，因此无需另存编号分配记录。

已发布、已展示及已退役编号不再分给其他目标。事务发布后丢失回执时，按预期版本和请求指纹读回原文件，不重新编号。两个不同请求竞争同一下一版本时明确冲突，不自动合并。

同一目标跨运行保留 pointId。定义变化由用例文件版本及该目标的内容指纹区分；不维护独立 pointRevision。业务意图变成另一目标、拆分或合并时新建编号，在版本内写明关系与退役理由，不凭标题猜等价。

### 3.3 一次保存不是一次测试

普通重测直接读取原用例版本，不写 v002；新增运行也不触发用例整理或规则沉淀。实际观察、定位细节和执行问题留在对应 run，只有需要修正定义或必要计划时，AI 才保存新版本。

同一工作目录由一个明确的协调者写入。文件锁不承担分布式目录合并；复制出的独立可写副本发生同版本不同内容时报告分叉，不静默覆盖或重排编号。

## 4. 人工审阅

AI 完成本次要求的测试点或可审阅用例草案后，生成 HTML/Markdown 并暂停依赖该设计的执行。只要求测试点就交付测试点；要求完整用例时交付足以评审的前提、必要步骤及预期，不固定增加两轮审批。

文档提供场景目录、编号检索、来源、预期、必要步骤与依赖、参数、覆盖和待确认项。意见可以按点或整个版本导出 JSON，AI 根据实际收到的意见修订。

审阅记录与用例文件放在一起，记录版本/文件指纹、覆盖的 pointIds、意见、实际确认来源及工具计算的目标定义指纹。用户一次明确确认可以覆盖整个版本，不要求逐点再次确认。

离线 HTML 的按钮及其导出的 approved 字段只表达文件内容；用户或已明确委托者的实际确认须有真实定位。确认文件不构成人类身份认证，不宣称能阻止有宿主权限的主体直接调用浏览器。

同一点出现较新的明确修改要求时，不能只挑旧确认绕过；普通补充意见不自动撤销确认，结论冲突或顺序未知时由 AI 澄清。本地校验读取相邻实际审阅记录，不新增审批状态服务。

重测不重复审阅未改变的用例。新版本只改了部分目标时，工具可读取旧审阅所对应版本，比较未变目标及其必要计划指纹，复用匹配的确认；业务标准、共享约束或必要计划变化的范围需要重新审阅。不能由 AI 写一句“没有语义变化”来替代校验。

已知资源缺口仍须尽早沟通。设计确认、当前资源就绪和真实操作授权是三个不同事实，不能因评审通过就推定账号或对象适用。

## 5. 三种执行范围

| 模式 | 正式判断范围 | 操作范围 |
| --- | --- | --- |
| points | 指定编号对应的目标 | 必要条件、路径及已声明步骤依赖闭包 |
| status | 指定历史状态命中场景的全部目标 | 保留既有整场景重跑语义 |
| full | 明确用例版本的全部在期目标 | 可执行部分及未准备范围分别保留 |

编号只在明确用例版本中解析，未知或歧义编号返回问题。零命中不转全量。AI 依据用户意图选模式，工具不静默替换。

例：一个场景有 TP-000001“下载完成”和 TP-000002“内容一致”。只重测第二点时，身份/对象核对、页面下载、保存原件和读取内容仍保留；只为 TP-000002 给本轮四态，不把准备过程中观察到的下载完成自动记成 TP-000001 本轮通过。

### 5.1 原用例快照与执行引用分开

每轮 baseline.json 保存本次采用用例版本的完整原件。run-binding.json 只保存选中编号、可执行/暂缓范围及执行所需的条件/步骤 ID，不再复制一份改写过的用例定义。

这只是冻结一份已有用例 JSON，确保以后仍能还原当时预期；不复制原始需求全文、代码、整个历史目录或旧证据，也不要求 AI 每轮重新生成用例。

points 模式对 selected goals 的 requiredRefs 和 steps.dependsOn 求闭包；条件 ID 不因筛选重排，strict 保留原相对顺序，非空必经路径始终保留。工具不补猜遗漏的业务依赖。

record 和工作包只允许为选中目标提交评估。基线中存在但未选中的点没有本轮状态，不能继承历史通过；为完成前提执行其他步骤不扩充评估范围。

### 5.2 全量、缺口与计数

AI 对照最新已确认需求核对用例版本，保存来源覆盖说明。新需求尚未形成目标时作为覆盖缺口显示，不能因不存在旧结果而遗漏，也不能伪造编号和四态补齐统计。

全量不按历史状态、任务成熟度或资源是否就绪过滤。已定义但计划未准备、待审阅或暂缓的点仍在本轮选择目录，无法执行的理由明确列出；AI 对确实未执行的点显式记录未测试。没有评估仍显示缺评估，程序不自动赋状态。

报告保留源场景→目标层级，分别显示源用例总数、选中目标数、可执行场景数、未准备/暂缓项及缺评估。四态只统计本轮选定范围的正式评估。

## 6. 每轮记录与历史对照

### 6.1 延续现有事实体系

沿用 manifest、baseline、results、evidence、execution 和工作包；继续使用 caseId/goalId 入账，通过基线解析稳定 pointId。复用 observations、contexts、actionEvents、findings 及 attempt/final，不建立另一份目标结果目录。

关键动作关联实际身份/对象/输入、即时回执、独立读回及自己的证据。共享材料说明支持范围，缺逐步取证时保留缺口，不从计划补造现场。串行与并行使用同一校验器，默认串行保持。

每次用户要求独立复测创建新 run；普通动作尝试继续用已有 actionId 区分。结果修订、重评旧观察和重新生成报告不算新一轮，不新增强制 executionId 管理体系。

### 6.2 通过运行引用关联

新 run 的 manifest/binding 记录原运行目录、runId、baseline 指纹及精确 resultsRevision/resultsSha256，必要时列多个父运行并明确主要比较基准。不维护项目级 runs 索引或 series 库。

AI 可在指定工作目录的 runs 子目录只读定位已有 manifest；比较基准必须明确保存，不按文件时间或相似标题猜原问题。目录移动时接受显式位置映射，不扫描用户其他目录寻找资料。

首次报告没有父运行时正常展示结果，不显示空历史面板。后续按 pointId 展示原结果、所选基准和本次结果，历史材料保留来源 run。分支比较不自动合并成单一修复过程。

### 6.3 原问题直接引用旧记录

问题保存在各 run 的 findings、phenomena 和评估中。复测时引用“源运行＋findingId”，或精确原评估/现象定位，记录 reproduced、not_observed、unclear、not_checked 及依据；不创建独立 issue 库或问题修订对象。

同一目标可有多个问题。旧现象未再观察到但出现新现象时，分别记录旧问题检查与新发现。原问题状态、目标四态、可比性和修复归因分别表达，不能仅凭违反转为已验证认定某提交修复了问题。

### 6.4 三轮示例

| 情况 | 用例资料变化 | 运行资料变化 |
| --- | --- | --- |
| 首次测试十个点 | 保存并审阅 v001 | 新建 run-001，保存十个点实际结果 |
| 重测两个原问题点 | 继续使用 v001，不生成新用例版本 | 新建 run-002，引用 run-001，只统计所选两点 |
| 某点需求确有变化 | 保存 v002，说明变化并审阅受影响范围 | 新建 run-003，展示准则差异，不把需求变化当代码修复 |

## 7. 参数与操作复用

参数定义放在相关用例内，说明类型、用途、必要关系和允许替换条件。本轮实际值及其核验依据放在 run-binding，不把账号、日期和对象变化都转化为用例版本。

步骤与预期保持可阅读的业务语义，例如“保存名称应等于本轮输入名称”；绑定值另表展示，不新增 TextPart 模板语言或表达式解释器，不全局替换或放宽固定业务标准。关系是否等价仍由 AI 核验。

通用截图、读回及下载辅助函数随工具维护。项目中特别稳定且有复用价值的操作，可以作为普通脚本及适用说明保留，由 AI 显式选择；不默认每轮抽取 helper，不建立组件注册库，不自动重试、换对象或绕行。

历史规则/任务资料保持原样；需要复用时，AI 从可信依据及实际运行整理到当前用例和执行上下文。规范与实际观察继续分源，不把现有 UI 结果改写为业务规则。

## 8. 下载与文件检查

下载主体复用 Ego 官方 page.waitForEvent('download') 和 download.saveAs()，本项目补充本次文件关联、独立保管、类型化读取及证据衔接。详见[下载设计](v0.1.8-download-design.md)。

原生事件漏收时，AI 可以显式使用已验证的下载管理页补证方法；该方法依赖安装版本及内部页面，不静默变为 fetch 或最新同名文件扫描。浏览器原生提示需要用户处理时交接同一 Space。

通过既有执行协调记录一个当前在途下载标记，避免本任务并行原生监听互相影响；不再新增独立资源租约或三个租约命令。未知结果不按时钟自动清除，AI 先对账。该约束不隔离外部对话或用户下载。

文件检查采用 Node 内只读能力，复用已验证的 CSV/XLSX 读取依赖并预打包。原件、下载事实和解析输出进入现有 evidence/record 链；解析器不输出业务通过。公式缓存、空值、部分读取等限制保留；首批读取已在 Node 22.20.0 与 24.19.0 实测。

## 9. 阅读器与交付

保留现有报告方案 B 的目标、实际步骤与证据并排阅读，增加稳定编号、用例版本、原问题检查及历次运行对照。原始字段与技术错误折叠，不把资产管理细节放进用户阅读流程。

HTML、Markdown、JSON 使用同一报告模型。当前结论引用本轮证据；历史图保留原来源，未选点只作历史上下文。报告筛选、主题和历史浏览不执行测试，也不回写账本。

需要携带下载原件或历史附件时，delivery=auto 解析为 bundle；其他情况可为 inline。显式方式仍支持，缺失材料不能用摘要冒充完整交付。只收集本次报告实际引用的材料，不复制整个项目历史目录。

本轮已登记证据沿用严格完整性检查；历史缺失可交付明确标记历史不完整的本轮报告。原运行、报告和图片不覆盖，三格式一致性与实际浏览分别核验。

## 10. 接口与改动边界

| 能力 | 收敛后的入口 |
| --- | --- |
| 用例版本与编号 | cases save；保留 validate-cases 的只读校验 |
| 用例文档 | cases render / verify |
| 意见及确认 | cases review，一个记录格式保存实际意见或确认 |
| 选择与冻结 | regression select / context / compare；start 继续接收 cases 与 binding |
| 事实与执行 | evidence-add、record、execution、packet-seal 延续 |
| 文件与报告 | files inspect、report、verify-report；Ego 辅助函数由 AI 脚本显式调用 |

不引入 asset read/validate/commit、point 注册服务、issue 管理入口、独立 review 服务或通用模板引擎。规则/任务管理能力并入用例与运行上下文，新版不再以前置提交规则/任务对象作为执行条件。

主要实现位置是现有 core/cases、baseline、records，回归 selection/binding/compare，执行与报告模块；只增加必要的用例版本/审阅及文件读取辅助。复用锁、不可变文件发布与哈希，不抽象通用 AssetStore，也不新建 src/assets。
