## 1. 设计决定

- **先 C 后 B。** C 独立验收公共能力的集中复用和职责边界；B 在这些能力上增加轻量读取。C 的价值同时包括维护性、可测试性和减少重复实现，不只用查询耗时评价。
- **封装确定性能力，保留 AI 决策。** 公共模块负责解析、校验、文件归属、哈希和状态快照；AI 决定何时查询、用什么视图和校验深度，以及业务路径、分派、补测、暂停和结论。
- **两种读取共用一套底层规则。** 元数据读取和完整检查复用相同的基线／台账解析器；B 省略历史证据正文复核，不另造宽松解析器。
- 默认并发保持 1，用户显式配置更高上限的方式不变；现有名额、资源与 Space 归属保护继续有效。当前限额和冲突检查作为回归基线保留。[VERIFY: src/execution/config.mts:12-28] [VERIFY: src/execution/ledger.mts:141-146]

## 3. C：公共能力模块设计

以下是拟议模块；本轮尚未创建程序文件。

| 模块 | 集中封装的能力 | 主要引用方 |
| --- | --- | --- |
| 新增 `core/baseline.mts` | `normalizeCases`、`newSafeCases`、`readAndValidateBaseline`；统一字段、ID、业务步骤、澄清项和冻结哈希校验，返回原结构。 | init／start、用例校验、原运行检查、worker 封包、新元数据查询。 |
| 新增 `core/file-integrity.mts` | 普通文件检查、单文件流式哈希、run 内引用路径与保留引用；集中现有 `hashFile/referencePath/retainReference` 实现及必要的文件存在性检查。 | 证据登记／恢复、运行引用校验、Space 创建回执、封包、导入和报告取证文件解析。 |
| 新增 `execution/read-context.mts` | 在调用者持锁时读取 manifest／baseline／execution，复用公共校验，检测待恢复标记，组装元数据快照。 | `summary`、`assignment` 的轻量读取。 |
| 调整现有 `execution/views.mts` | 继续只做分页、预览、计数和投影，接收检查范围及待恢复提示。 | 轻量与严格查询共用。 |

文件能力的边界：

- run 内引用、worker 目录内相对路径、正式 `evidence/` 路径继续使用明确的范围规则。抽公共哈希不替代这些归属检查。
- 大文件只需哈希时复用流式计算，避免为哈希把整个文件装入内存；确实需要解析的 JSON 仍读取字节，保持解析内容与对应哈希一致。
- 文件名、SHA-256 算法、字节计数及保留引用格式不变。符号链接／junction、路径穿越、非普通文件和分派错配的拒绝要求保留。
- 封包内重复的 worker 路径规则可先作为模块内部具名函数共用，不要求每个小函数都增加一个公开模块。

依赖要求：新基线和文件模块只依赖数据契约、通用文件／校验能力，不反向依赖 init／start、结果事务或查询编排。上层组合这些公共能力，投影层不读取文件。整体静态运行时依赖保持无环。

原有公开函数位置必要时用一行 re-export 保持调用入口；内部调用改为直接引用实现模块，不复制函数体。清理本次触及模块的无用 import，不扩展成全仓格式重写、通用仓储框架或依赖注入系统。

## 4. B：查询视图与检查范围独立选择

建议只增加一个 `--integrity metadata|full` 选项。以下为拟议接口，当前不可用：

| 调用 | 返回内容 | 检查范围 |
| --- | --- | --- |
| `execution read --run-dir ABS_RUN` | 默认 summary | 默认 metadata。 |
| `execution read --run-dir ABS_RUN --view assignment --assignment-id ID` | 一个分派及相关引用 | 默认 metadata。 |
| `execution read --run-dir ABS_RUN --integrity full` | summary | 完整校验；核验证据后仍只给少量输出。 |
| `execution read --run-dir ABS_RUN --view assignment --assignment-id ID --integrity full` | 一个分派及相关引用 | 完整校验。 |
| `execution read --run-dir ABS_RUN --view full` | 原完整输出 | 始终完整校验，保持兼容。 |

`--view full --integrity metadata` 明确拒绝；`assignment` 继续要求精确 assignment ID。非法选项不会静默换模式。AI 可按需要直接选任一种合法组合，工具不规定必须经过哪些业务步骤。

### 4.1 元数据读取内容

1. 复用已有运行锁，读取 manifest、冻结 baseline 和 execution JSON。
2. 校验 manifest 版本／固定文件引用，比较冻结基线哈希，调用同一用例解析器和 `parseLedger/readExecution`，核对 run、case、baseline 与操作关联；历史文件引用复用纯路径规则检查穿越和目录范围。不会因为是轻量路径就跳过结构校验。[VERIFY: src/execution/ledger.mts:70-88] [VERIFY: src/execution/ledger.mts:111-115]
3. 检测 `.evidence.pending.json` 是否存在及其路径是否安全；显示“有恢复标记”，不据此保证事务可以恢复。待导入数和引用继续来自台账。
4. 不读取 `results.json/evidence.json` 做跨文件完整检查，不读取历史截图、worker 创建回执和 packet 文件正文，也不核对其当前哈希；execution JSON 中已有的 packet 快照仍须随台账解析。
5. 快照读取／校验完成后释放锁，再做输出投影和序列化；继续明确标记列表和文本截断。

元数据查询不调用 `recoverEvidence`，不更新 execution／results／evidence，不自动导入或续接。运行锁的临时文件仍按原机制创建和释放；锁忙时返回明确错误，由 AI 决定后续动作。

实际读取的 run／manifest／baseline／execution 及恢复标记路径继续做安全路径和普通文件检查。历史引用只核对文字路径范围，不逐个确认物理文件是否存在、是否被改成重解析点；这些属于本次明确未检查的证据完整性范围。轻量查询不打开或跟随这些历史引用，后续严格读取／提交仍须在实际访问时拒绝不安全文件。

严格读取、写入、导入、`check/report/verify-report` 继续使用完整检查；既有严格路径的确定性证据事务恢复保持原行为，不增加业务重试。当前完整检查和报告路径是此次兼容基线。[VERIFY: src/core/records.mts:256-258] [VERIFY: src/report/delivery.mts:50-66]

### 4.2 返回值明确说明检查范围

建议将 summary／assignment 的查询契约升级为 `viewVersion:2`，例如：

```json
{
  "viewVersion": 2,
  "view": "summary",
  "integrity": {
    "scope": "metadata",
    "baselineHash": "matched",
    "executionLedger": "validated",
    "recordedResults": "not_checked",
    "evidenceFiles": "not_checked"
  },
  "recovery": {
    "evidenceMarker": "present",
    "pendingImports": 1
  }
}
```

此示例只展示新增语义，不是完整响应。完整检查的紧凑视图使用 `scope:full`，相应标记为 `recordedResults:checked`、`evidenceFiles:verified`。两种模式都不认证截图真实性或重新作出业务结论。

单分派返回的状态、目标评估等是已记录内容。若轻量查询没有重查证据，即使记录中有 verified／pass，也不能把它描述为“本次已重新核验通过”。子 Agent 的实时状态仍由主 Agent 通过宿主工具观察，台账不自动探测宿主或监控 worker。

## 5. 兼容、版本与数据保护

- C 阶段先保持当前行为，单独回归。B 阶段建议使用新开发修订 `0.1.4-dev.3 / ts-parallel-3`，更新 Schema、生成类型、资源清单、调用指南和版本检查；本轮方案不改实际版本。
- 查询契约 `executionRead` 从 1 升 2；`integrity` 从固定字符串改为检查范围对象，不能在相同契约版本下悄悄换语义。当前 v1 的完整检查标志作为兼容变更依据。[VERIFY: schemas/execution-read.schema.json:4-19]
- CLI 默认查询的新语义是元数据检查；依赖“查询成功即表示证据已重新校验”的调用方须显式加 `--integrity full`。`--view full` 与原 `readExecutionView` API 继续严格校验并保持原完整返回结构。
- 不改 cases／results／evidence v3、manifest／report v4、execution／configuration／workerPacket v1。不迁移旧 run，不覆盖原报告、截图、冻结包、基准数据或用户级安装。
- 不增加持久化缓存、文件索引、数据库、后台线程或自动调度。依然需要读取和解析完整台账，不承诺记录无限增长时查询保持恒定时间。

## 7. 性能测量安排

沿用 A／D 的合成基准工具思想。此前 100 用例／1000 历史记录／50 文本证据时，默认摘要为 5153 字节、最终中位约 246 ms，每次仍读取 3,510,000 字节证据；这是比较基线，不是 B 的预期结果。[VERIFY: docs/v0.1.4-ad-validation.md:33-49]

- 固定历史记录量，对比无证据、约 3.5 MB、约 50 MB 三组纯合成证据；后两组尽量固定文件数量，区分字节规模与文件数成本。
- 固定证据量，对比 100／1000／5000 条有效历史操作，观察台账解析和关联校验成本。造数与校验准备时间单列。
- 每种合法视图／检查组合预热 3 次、采样 10 次，比较端到端中位数和尾部样本、输出字节、各类文件读取次数／字节及成功持锁时长。小样本尾部只作为观测，不包装成稳定生产 P95。
- 增加受控的查询／写入交错实验，记录成功、锁冲突与 revision 冲突；不添加自动轮询、抢锁、强制解锁或业务重试。
- B 的硬验收是避免历史证据正文读取并正确声明未校验；耗时收益按实测交付，不预先承诺固定倍数。C 单独按复用、依赖和行为保持验收，即使小数据总耗时相近，也能完成其代码质量目标。

本方案提出时新增能力为未实现、未测试；随后批准的实施结果见上述验证记录。原 A／D 验证和真实 UAT 记录保持各自原有结论。
