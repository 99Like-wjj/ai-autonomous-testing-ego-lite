# 测试附件进入报告的优化方案

日期：2026-11-06。状态：A1、A2及评审Demo已获用户批准，已完成实现与本地验证，见[完成记录](../evaluations/attachment-review-20261106/validation.md)。原方案基线：`c4e7e87` / 0.2.1-rc.1。本文保留审核时的设计依据；用例阶段不生成附件。

## 1. 当前结论

现有报告已经有附件交付底座，但没有完整、清晰的“复测文件”体验：

- `auto`只在历史材料、对话或显式要求交付等条件下转bundle；普通上传输入即使已经作为证据登记，也可能仍用inline。本次合成样本实际得到`inline / complete=true / attachments=0`。此处complete是当前交付契约的结果，不能据此推断测试输入均有直接下载入口。[VERIFY: src/report/delivery.mts:206]
- bundle会交付已登记、未排除的文件；文件仅在执行目录存在，不会自动被扫描进报告。目录自动打包也不应作为修复办法。[VERIFY: src/report/assets.mts:62-83] [VERIFY: src/report/assets.mts:102-103]
- 目前附件文件名以hash为主，只区分少数扩展名。CSV在样本中成为`<hash>.txt`，二进制成为`<hash>.bin`；HTML的下载链接没有指定可读的原文件名。[VERIFY: src/report/assets.mts:49-51] [VERIFY: src/report-ui/main.ts:248-256]
- 对话已经支持`attachmentSourceIds`，但当前点击附件先打开通用证据弹窗，再点“打开留存附件”。输入/输出用途、原始文件名和复测下载不是主展示信息。[VERIFY: src/report-ui/conversations.ts:41-43]
- 图片内嵌展示目前走screenshot分支；普通文件的预览主要按UTF-8文本处理。上传用图片或AI输出图片不能为了获得预览被错误标成“截图证据”，需要将文件用途与媒体预览类型分开。[VERIFY: src/report/assets.mts:84-100]
- 强制inline时，必须交付的下载原件缺少独立文件会被标不完整；不应为了“单个HTML”静默丢掉附件。[VERIFY: src/report/assets.mts:98-103]

上述结论基于源码及独立的本地合成HTML；没有重跑真实业务或修改用户报告。合成观测见[记录](../evaluations/reader-audit-20261106/observations.json)。

## 2. 建议采用的用户体验

### 报告中直接取得“这一步用的文件”

每个目标的实际步骤详情增加“本步测试附件”，放在输入/回复摘要旁边，而不是藏在原始证据或hash元数据里。

```text
本步测试附件（2）

input-data.csv             25 B · 测试输入 · 本轮生成
用于：第2步上传              [下载原件] [预览] [文件信息]

result.xlsx              120 KB · 下载结果 · 来自被测系统
用于：第3步导出              [下载原件] [文件信息]
```

首层显示名称、类型/大小、用途、来源和可取得状态；hash、登记ID、内部路径放到“文件信息”内。按钮明确叫“下载原件”，避免“打开”实际是下载。

### 同时提供全局“测试附件”入口

报告顶部增加“测试附件”，列出本轮与复测有关的文件，可按场景/目标、输入/输出和名称筛选。文件行可回到对应步骤；同一原件被多个步骤使用时显示关联，不重复制造多份文件。普通日志、规范化对话JSON、截图仍可在证据库查看，不全部混成复测文件。

建议第一批支持逐文件下载；“下载全部测试附件.zip”作为可单独选择的增强项。若做合集，在报告生成时预先生成静态ZIP及清单，避免离线页面运行时跨本地文件读取或依赖临时服务器。合集只含本轮授权的复测材料及说明，不夹带无关日志或目录内容。

### AI对话中也使用同一种文件卡

用户消息显示“输入附件”，AI消息显示“输出附件”；可预览、直接下载、查看关联步骤。现有来源映射继续用于保真核验，但人不应为了拿到输入文件先翻原始JSON、再打开两层弹窗。

查看/下载附件不切换当前目标，不清空步骤、资料选择或聊天阅读位置；关闭预览回到原位置。文件操作同时纳入[交互清单I06/I07](reader-navigation-audit-20261106.md)。

## 3. 四类场景如何处理

| 场景 | 必须保管的材料 | 报告显示 |
|---|---|---|
| 普通功能上传 | 实际交给文件选择器的原件、当时文件名 | 测试输入；关联上传步骤；直接下载同一文件 |
| 普通功能下载 | 被测系统实际下载的字节、实际建议文件名及取得依据 | 下载结果；关联下载/导出步骤；不要用本地重造文件代替 |
| AI对话上传 | 实际消息附件原件、消息/步骤归属 | 用户消息中的输入文件卡及步骤附件区 |
| AI生成/返回附件 | 真实取得的AI产物；如后来另行下载，保留实际下载关联 | AI消息输出文件卡；区分“AI给了链接”与“原件已保管” |

输入可以在执行时按用例要求生成，也可能由用户提供；来源如实记录。系统下载和AI输出应保留实际原件，不能为方便展示而重新生成、改内容或冒充原结果。格式异常的反例文件同样保留当时字节与扩展名，才能复测。

文件可用性与业务结果分开。例如可以显示“原件已保管，上传结果仍未知”；附件存在不使业务目标自动通过。

## 4. 留存与关联设计

沿用现有evidence登记、hash、文件所有权、动作事实及对话映射，不另造一套项目附件库。

建议增加两类最小信息（本方案中的字段名为提议）：

1. **文件本身的描述**：在证据metadata中标明它是测试文件，保存实际文件名、来源类别及已知生成/获取信息。大小与hash复用现有目录；媒体类型复用现有字段，不再维护冲突的副本。
2. **这一步如何使用文件**：实际动作关联文件evidenceId，并声明上传输入、下载输出、AI输入或AI输出。复用同一原件不复制字节；用途归属动作，不把一次用途固化为文件永远只能输入或输出。对话继续使用消息的attachmentSourceIds映射到同一原件。

上传前生成/选择材料时及时留存；下载成功后由捕获回执关联实际文件。辅助工具可以确定性地复制、hash和准备登记请求；AI确认真实来源、动作关联、获取是否完成及业务结果。没有成功下载的原件，工具不能伪造文件记录或自动重发下载。

现有metadata目前只有有限的artifactRole和deliveryRequired等字段；新增描述、关联及worker导入映射必须同步Schema、生成类型、验证和报告，不能只在HTML里加一段文件名。具体格式影响在获批实现时明确，旧用例、运行和原始证据不自动迁移。[VERIFY: src/core/validation.mts:180-194]

## 5. 离线包与链接

- 默认使用可移动的`report.html + attachments/ + 清单`，附件链接相对报告目录。文件有测试附件描述时，auto应把需要复测的原件纳入bundle。
- 原件物理文件可采用“hash目录/安全的原文件名”，同时在下载属性指定实际可读文件名；不再强制把CSV交给测试人员时变成TXT。内容hash继续核验，显示名与实际字节保持区分。
- 重名文件通过独立物理位置消歧；同字节不同名称/用途仍保留各自逻辑信息。不能只按文件名覆盖，也不能只按hash把两个测试角色抹成一个。
- 主操作提供“下载原件”。复制路径若提供，应明确是“附件相对路径”或“本机文件链接”；本机file链接不伪装成同事可访问的互联网地址。
- 需要在线分享时，可由用户把完整报告包放到已有受控站点；本功能不默认上传、开服务器或生成所谓永久地址。不依赖原机绝对路径、blob地址或带凭据的临时链接。
- 预览支持明确的安全类型；其他类型仍可下载。附件原件不得在报告中当HTML或脚本执行，不能通过改写文件字节来“安全化”复测材料。
- 类型分发复用已支持的图片/文本预览，但不改变文件的测试角色；声明类型、扩展名与实际字节不一致时如实说明，保留格式异常测试输入，不能自动改扩展名或内容。
- 当前路径白名单也必须随新存储布局按清单统一调整，不能放开成任意本地路径/协议。[VERIFY: src/report-ui/conversations.ts:23] [VERIFY: src/report-ui/main.ts:248]

## 6. 缺文件与历史材料

| 实际情况 | 处理 |
|---|---|
| 原件已留存且hash匹配 | 允许预览/下载，显示真实来源与关联 |
| 当时未取得、下载未知、策略未保管 | 显示具体原因，没有可用文件时不提供假下载按钮；列入复测材料缺口 |
| 原本登记的文件后来丢失或hash变化 | 保留完整性错误处理，不悄悄换成同名文件或略过核验 |
| 只有外部位置或权限受限链接 | 显示资源位置、访问前提和有效性限制；不能声称原件已交付 |
| 文件在磁盘但未能证明被哪个目标使用 | 不自动挂给所有用例；全局标“尚未关联”，由有依据的整理补关系 |
| 需要给旧报告补充 | 保留原报告/台账，基于可核验原件另导新报告，标明后补关联；不为补附件重跑真实业务 |

建议在交付检查中增加“复测附件完整性”，与字节完整性、业务四态分别呈现。正常报告可如实列缺口，但不能在缺少必要复测文件时只用一个绿色“完整”掩盖问题。已排除/未获准交付的内容不会因新入口被自动打包。

## 7. 用例HTML如何衔接

设计/评审时尚未生成的材料，只说明所需文件规格和“执行时生成”，不伪造下载链接。已经存在并获准使用的固定样例可有真实引用。

本次生成的附件属于run事实，建议优先在报告对应目标与步骤中交付；不得把执行后原件直接塞回冻结用例，造成用例hash/审阅依据被改写。若还需要“从用例页访问某次运行附件”，可另导有明确run/revision来源的派生阅读文件，作为可单独决定的增强项，不覆盖原用例HTML。
