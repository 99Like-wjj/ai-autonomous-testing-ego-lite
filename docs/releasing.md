# 打包与发布指南

本指南面向维护者和参与开发的 AI。它是仓库文档，不是 Skill 运行资料，不进入安装包。用户安装、升级和加载验证见仓库根目录 [INSTALL.zh-CN.md](../INSTALL.zh-CN.md)。

## 1. 先确认任务范围

- 修改代码、测试通过、推送分支，不等于获准合并或发布。遵守 [AGENTS.md](../AGENTS.md) 的当次审核与发布授权要求。
- 日常开发不默认生成或交付候选 ZIP 或独立安装目录。工程测试需要的临时打包验证可以执行，但不能将临时产物作为用户安装包交付。
- 正式发布前固定精确提交、版本和 revision。候选版本保留 rc 标识；未完成正式发布步骤时，不把候选版本冒充稳定版本。本指南不宣称某一版本已经发布。
- 不移动已有版本 Tag，也不悄悄替换旧 Release 附件。

## 2. 分发内容以白名单为准

[src/contracts/layout.mts](../src/contracts/layout.mts) 中的 `runtimeFiles` 和 `referenceNames` 是分发清单源。源文件维护 `.mts/.ts`，运行时分发构建后的 `.mjs/.js`；不要直接修补 `.build/` 生成物或手改 `runtime-manifest.json`。

安装目录应包含：

- `SKILL.md`、宿主元数据和运行所需的编译代码、报告及审阅页面资源。
- AI 实际使用的 `references/` 指南、数据契约、必要的合成示例和当前操作说明。
- 项目许可证、被分发的第三方依赖许可说明、运行身份及完整性清单。

以下内容留在仓库，不进入 Skill 运行目录：

- 需求前瞻、设计与可行性研究、历史整合记录、开发评测或验收记录。
- 版本演变图、宣传图片、完整版本历史，以及本打包指南、开发用 `AGENTS.md`。
- 源码、测试、构建工具、`.git`、`node_modules`、真实业务项目、报告和证据、凭据。

不能按扩展名删除全部 Markdown，也不能直接删除整个 `docs/` 或 `examples/`。当前操作资料和合成示例可能被 Skill 引用；精简前先迁移仍需要的内容。第三方许可文件不属于可省略的开发文档。

移出文件时同时检查 Skill、references、当前文档及安装说明中的链接。正常使用所需的信息保留在包内，不要求 AI 为基础操作联网；历史背景可改成固定 Tag 的仓库链接。不得为了修复仓库 README 的链接而把整套开发文档加入运行白名单。

## 3. 在确认的源码目录构建

先确认分支、精确提交和工作区状态，不覆盖他人未提交修改。使用仓库锁文件安装开发依赖，依据 `package.json` 的 Node.js 要求准备环境：

```sh
npm ci
npm run typecheck
npm test
npm run check:public
git diff --check
```

`npm test` 会先构建，包含契约和界面文案生成检查。工程检查不替代真实 Ego、Windows、客户端或业务验收；记录实际操作系统、结果、跳过原因和未运行范围，不能照抄上一版本的通过数量。

获准生成安装包后，在仓库外使用一个**尚不存在的绝对目录**：

```sh
npm run build:skill -- --output-dir <仓库外尚不存在的绝对目录>
```

实际使用时替换占位符并正确引用路径。`build:skill` 生成独立完整 Skill 目录，不生成 ZIP，不注册 Skill，也不更新用户本机；已有目标目录会被拒绝。不要将实际安装目录作为构建目标。不要直接压缩源码树或未经检查的旧 `.build/runtime` 暂存树。

## 4. 检查完整性，也检查是否多带文件

对构建目录和最终 ZIP 解压目录分别验证：

1. 运行 `node scripts/ego.mjs tool-info --expect-version <本次版本> --expect-revision <本次revision>`，核对身份、格式版本、`installationIntegrity` 及逐文件哈希。
2. 枚举**所有实际文件**，与当前源白名单展开后的文件集合比较。独立 Skill 目录只允许清单文件及生成的 `package.json`、`runtime-manifest.json`；不得残留旧版本退役文件。单独看 `tool-info` 的 `verified` 不足以证明目录没有额外文件。
3. stage-runtime 与 build-skill 自动核对完整文件集合和内联 Markdown 链接的本地目标文件；不验证标题锚点、引用式链接或 HTML href/src。另行检查这些引用、外层安装说明链接及关键指南、契约、示例、第三方许可和报告资源，按最终 ZIP 布局核对。
4. 执行相关 CLI、报告及打包回归测试。检查退役文件残留、文件篡改、缺失资源、干净目标目录，以及符号链接路径等边界。
5. 检查没有真实业务数据、日志、访问令牌、密钥或用户本机路径等不应分发的信息。

完整性清单随本次构建生成；从 ZIP 手动删文件或只改 manifest 不能替代白名单与编译产物同步修改。若构建发现旧暂存数据，按工具的明确错误检查其来源，不将未知或用户修改文件视为可直接删除的临时文件。

## 5. 生成 ZIP 和校验值

发布附件建议布局：

```text
INSTALL.zh-CN.md
ai-testing-ego-lite/
  SKILL.md
  package.json
  runtime-manifest.json
  ...当前白名单运行文件
```

将根目录安装说明的源文件复制到 ZIP 外层；不要把它连同开发指南塞进 Skill 运行白名单。版本、revision、格式变化和该次验证结论写进 Release 说明，安装说明保持可复用。

独立目录构建不负责 ZIP 和 SHA256SUMS，需要发布步骤另外完成。压缩后重新解压到全新临时目录，检查 ZIP 路径安全、CRC、文件集合、逐文件字节与 manifest，再运行身份和完整性检查。用最终 ZIP 的实际 SHA-256 生成 `SHA256SUMS`，不要用压缩前目录指纹替代 ZIP 哈希。

## 6. 发布与升级验收

- 对用户批准的精确提交核对版本、Skill 元数据、CLI、CHANGELOG、README 和 Release 文案；不要混用不同提交的代码与安装包。
- 获准后创建对应固定 Tag 和 Release，上传完整 ZIP 与 SHA256SUMS。GitHub 自动生成的 Source code ZIP 不是编译安装包。
- 发布后实际下载附件，核对哈希、大小与内容；将可安装包和源码包区别写明。
- 在独立测试目录验证从旧版到新版的升级流程：先查旧 manifest 和实际哈希，区分旧包未修改文件、用户修改、未知文件与真实业务数据。不得只叠加覆盖，也不得未经检查删除整个旧目录。
- 本机安装需遵从用户授权，并按安装说明确认真实加载路径。发布成功不意味着用户电脑已更新；新会话仍需验证加载版本。历史数据格式不支持自动迁移时，明确说明，不能只改 JSON 版本字段。

测试用目录不得冒充用户安装验收。报告哪些步骤通过、失败、跳过或未执行，提交审核后等待当次合并及发版授权。
