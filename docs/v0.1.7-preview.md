## 背景

维护者已在本地用一份需求试跑 v0.1.6，反馈代码可用、效果尚可。现有版本已具备阶段化经验指南、逐业务目标评估、接口观测与三格式报告。下一步应以实际发现的问题改进测试质量，而不是仅增加工具或规则数量。一次试跑不能推导通用成功率。

## 计划方向

### 1. 测试效果

- 改进需求到业务目标、用例和预期的映射，检查正常、边界、异常、权限、状态和依赖中与目标相关的覆盖，避免机械扩充用例。
- 核对设计经验与执行经验的适用阶段；扩写确有价值的误判和恢复场景，人工审核后维护，运行时保持只读。
- 优化 UI、接口及其他观察的相互印证，保留首次异常；未知副作用先核验，不能靠重试或弱化预期获得通过。
- 明确保留未测试、无法判断、资源缺口和额外发现，不以动作成功代替业务成功。

### 2. 评测标准

- 准备脱敏或合成的代表性需求、可核验预期、已知缺陷与正常对照；保存输入、实际输出、逐目标人工复核和证据位置。
- 分别评估需求覆盖、有效缺陷发现、误报/漏报、证据充分性、授权与数据安全、完成情况及时间/调用成本。没有可知缺陷全集时，不编造召回率。
- 区分工具结构回归、合成场景演练和真实业务试跑，注明模型、宿主、浏览器、版本及环境条件；重复试跑说明波动。
- 对比优化前后相同目标与输入，记录改善和退化；评分定义、权重与阈值经后续设计审核，不以单一通过率评价质量。

### 3. 报告格式

- 让读者先看到测试范围、结论分布、主要问题和阻塞，再按目标查看预期、实际观察与证据。
- 改善缺陷描述、复现条件、关键步骤截图及接口证据的关联和阅读路径；敏感信息须按授权处理。
- 分开展示业务结果、根因确认程度、执行状态、证据缺口与文件完整性；保留历史尝试及未完成项。
- 维持 HTML、JSON、Markdown 同源统计和结论，评估长报告的定位效率与可读性。

### 4. README 与示例

在首页合理位置展示已交付能力、使用边界、评测入口和报告示例。示意图与合成报告须明确标记，不冒充真实测试证据。README 版本演变展示仅保留最近四个已交付版本，不据此删除历史文档或资产。

## 边界与后续验收

- 本前瞻不决定数据库、RAG、强制流程或固定评分算法，也不增加运行时自动经验沉淀。
- AI 保留自主分析与方法选择；业务目标、必要语义、授权和事实要求保持不变。
- 依据当前目标选择设计，默认不为旧格式增加兼容层；若需改变格式，应先说明影响，不能删除或覆盖用户历史数据。
- 下一步详细设计应列出具体改动、验证场景、人工评审要求与接受标准，经审核后开发。移动端执行层仍是独立调研，不在本前瞻中承诺交付。
