## 1. 推荐方案与范围

本版完成两项用户目标：

1. 用户进入版本演变页，能看懂各版本解决什么问题、增加什么能力、怎样影响使用。
2. AI 根据具体测试目标发现资源缺口，在授权内先核验，必要时主动询问；暂停依赖缺口的动作，补充资源后核实再恢复，报告保留未验证范围。

推荐采用“清楚且会被加载的行为规范 + 按需简短资源记录 + 复用现有工具”。第一版不新增独立资源管理引擎、强制审批表或资源 JSON 契约。现有结果、证据和交付包能够承载必要事实，避免维护两套容易漂移的状态。

AI 决定需要什么资源、哪些目标受影响、问什么及如何继续。工具负责文件、引用、事务和渲染，不判定资源是否充分，不自动选择业务路径或重试。

### 2.2 外部调研的取舍

- [Gemini CLI ask-user](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/tools/ask-user.ts)区分取消、空提交和真实答案。采用这种语义，复用宿主问答工具；收到答复后仍需核验，不把“已回答”当“已就绪”。
- [Playwright fixtureRunner](https://github.com/microsoft/playwright/blob/main/packages/playwright/src/worker/fixtureRunner.ts)会避免执行依赖失败的函数。借鉴受影响范围停止的原则，由 AI 分析依赖，不复制固定 fixture DAG。
- [Playwright 认证说明](https://playwright.dev/docs/auth)区分认证状态、角色与共享服务端状态。它描述 Playwright 的能力，不能据此证明 Ego Space 具备相同隔离效果。
- [Cline 问答与审批源码](https://github.com/cline/cline/blob/main/apps/cli/src/utils/approval.ts)分别处理问答和审批；当前非交互问答仍有返回首选项的行为。本项目不采用默认代答。
- [Keep a Changelog](https://keepachangelog.com/en/2.0.0/)支持面向使用者整理变化；[GitHub Release 文档](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository)说明发布说明与附件的关系。演变页据此组织介绍，正式发布仍遵守项目的精确 Tag、安装包和校验要求。

这些是设计借鉴，不引入相应框架依赖，也不证明本 Skill 已实现这些能力。

## 3. 资源主动澄清的行为设计

### 3.1 入口约束与加载

建议在 SKILL.md 保留以下核心要求，并明确链接新增 references/resource-readiness.md：

> 根据当前测试目标判断必要身份、权限、环境、数据、隔离和观察条件是否充分。先用已有资料及授权内的安全核验消除未知。仍有影响正确性、有效性或授权边界的实质缺口时，说明缺口、受影响目标及需要用户补充的内容；解决前暂停依赖它的动作。允许继续前提成立且已获授权的独立工作。补充信息后核验相关条件再恢复，执行中发现新依赖时同样适用。

形成初步目标、评估可执行性时读取资源指南；执行、恢复中有新条件时按需重看。用例编写、并发和判断指南链接同一份说明，避免重复维护。维度只是推导提示，不要求每项目填同一张清单，也不要求每次点击前重读指南或通过全局闸门。

接收外部用例和 AI 生成用例都适用。仅生成用例时，可以交付注明前提的草案；资源不足不禁止分析，也不能把草案描述为已经可执行。

### 3.2 三类问题分别处理

| 类别 | 示例 | 处理方式 |
| --- | --- | --- |
| 验收歧义 | 低权限角色究竟允许哪些操作？ | 使用既有 clarificationQuestions 契约；澄清后验收改变则修订并重新冻结。 |
| 资源可用性 | 规则明确，但没有低权限账号。 | criticalConditions 表达所需前提；运行观察和剩余问题表达缺口，不改验收字段。 |
| 操作授权 | 账号能删除，但是否允许删除这批数据？ | 核对用户已有授权，只暂停未获授权动作；技术可操作不构成授权。 |

同一事项可能包含多类未知，分别说明。例如 coding 的产品含义不明，与尚未获得对应权限是两项问题；不能解释为管理员权限、Codex 权限或允许修改代码。

### 3.3 何时问，怎样问

AI 按目标和事实判断，不因某字段未填写就机械提问：

- 已提供且可安全核验的内容先查；不重复索取。
- 无法在已有授权内自行确认、且影响正确性/有效性/授权的实质问题，主动询问。
- 说明缺什么、为什么需要、影响哪些目标、用户可以怎样补充；合并相关问题。
- 使用宿主问答能力；没有相应工具时使用普通对话。取消、空答、工具失败、无人回复及部分回答，都只保留实际未决项，不能默认同意或代答。
- 必要答案尚未到达时暂停依赖动作；独立工作由 AI 判断是否继续。
- 用户可以使用已有会话或自行登录；不要求在聊天、JSON、用例或报告中填写密码、token、验证码。

在用户描述的信息确实未明确时，期望表现示例：

> 跨角色检查需要两个不同角色。目前只核实了一个账号，因此低权限及跨角色部分暂时不能执行。请提供另一个角色的可用登录方式，或在 Ego 中完成该身份登录，并确认其在目标项目中的角色。需求里的 coding 对应哪个产品权限项？本次可操作的隔离项目及允许修改、清理的范围也尚未明确。其他前提成立的独立检查可以继续。

这不是固定模板；普通项目不因此被强制要求两账号、coding 权限或隔离项目。

### 3.4 补充后恢复与真实性

“补好了”是待核实线索。AI 核对实际身份、角色、环境与对象适用性后再继续；事实有时效，恢复时按风险复查，不能把之前的 available 当永久事实。

补充内容满足原冻结条件时，可以在原运行保留受阻记录并新增观察。如果改变冻结的具体角色、项目、输入等必要语义，则保存依据，修订用例并重新冻结。恢复不自动重放操作；先核对可能已生效的业务副作用，保留首次错误。

角色尚未核实时出现拒绝，不能直接判产品缺陷；低权限身份和明确拒绝规则均核实后，若成功完成禁止操作，则可据有效证据报告违反，不能统一解释为资源不足。

## 4. 记录、工具、并发与报告

### 4.1 按需记录，复用现有数据链

简单场景使用对话和运行记录。多轮恢复、跨 worker 汇总有需要时，在仓库外的私有工作区维护简短 resource-notes.md。它是 AI 工作记录，不是强制新文件或执行许可。

建议记录：简短标识、资源需求及用途、受影响用例/目标、用户提供与实际核验事实及来源/时间、可用性、授权、问题、答复、核验与恢复决定。事实变化追加原因和时间，保留受阻历史；不用一个 ready 值混合“存在、核实、授权”。

不保存密码、token、cookie、storageState、验证码或可兑换登录链接。公开示例仅用合成内容；结构校验和模式扫描均不保证没有秘密。

| 重复工作 | 复用工具 | 边界 |
| --- | --- | --- |
| 保存受阻原因与剩余问题 | record，或 packet-seal 后由协调者 import | AI 提供事实和判断；工具校验结构、引用和修订。 |
| 查询范围 | progress 看状态/用例 ID；check 按需读完整记录 | pendingClarification 仅统计冻结验收疑问，不是所有资源缺口。 |
| 保存核验依据 | evidence-add 或 worker 包 | 需要留存时登记脱敏快照；hash 只证明字节一致。 |
| 保留补充前后历史 | 新操作 ID、attempt/final、原始 packet | 数据事务幂等不表示业务可以重放。 |
| 交付核对 | report、verify-report | 核对已集成的运行和证据，不自动校验旁边的资源笔记。 |

正式报告所需事实须进入现有结果、目标评估和证据链。未集成的 Markdown 笔记只是辅助，不能声称通过 verify-report。若实际验收证明反复丢失或查询成本明显，再基于事实设计独立资源事务，不提前引入第二套状态。

### 4.2 并发和串行衔接

协调者汇总用户问题和答复；worker 发现新缺口，暂停依赖动作，交回事实、受影响目标和问题，不擅自扩权。多个 worker 缺同一资源时合并提问，同时保留不同目标的权限和数据要求。

公共记录由协调者单写；worker 只写自己目录并封包，协调者复核导入。暂停/恢复如实记录在途状态，不直接假定业务已停止或回收名额。

资源齐备和并发安全分别判断。不同 Space 不证明账号、cookie 或后端隔离；继续使用现有互斥键及授权限制，默认并发仍为 1。

需在 v4 报告精确呈现四态时，串行可由当前 AI 使用现有分派、封包、导入接口，无须创建子代理。源码目前只从已导入的显式 goalAssessments 投影具体目标评估；只调用旧 record 不会自动生成这些评估。不为提问强制创建 Space 或 worker。

### 4.3 报告表达

| 实际情况 | 用例记录 | 目标表达 |
| --- | --- | --- |
| 已知资源/授权障碍阻止检查 | blocked，说明障碍和问题 | 未开展该目标检查为未测试；已有观察仍不能判断时为无法判断。 |
| 已尝试，身份或后果仍不确定 | inconclusive，保留观察 | 受影响目标无法判断，其余目标各自按事实判断。 |
| 补齐资源后完成有效验证 | 新结果/观察，保留受阻历史 | 有充分证据的目标才可已验证。 |
| 条件有效，违反明确业务规则 | 据证据记录 fail 及合理归因 | 对应目标发现违反，其余目标仍独立说明。 |

这是表达原则，不是让代码从用例状态自动推导目标结论。blocked 不变成第五种目标状态，缺资源不直接判产品缺陷，已核验前提也不代表依赖目标通过。

沿用 HTML/JSON/Markdown 交付，展示影响目标、实际完成范围、缺口、待补内容和历史。没有执行 UI 检查不伪造截图；已有关键 UI 结论仍须真实截图。若尚未进入实际执行，只交付草案和澄清事项，不为凑报告制造执行记录；已开始运行后结束则完整报告未测试/无法判断范围。

## 7. 验证与验收

工程验证完成类型、契约、全量测试、公开文件检查及独立安装包核验；新增回归聚焦可观察行为：

- 资源受阻记录允许无产品结论，不污染冻结验收问题。
- 原条件下补资源后保留受阻历史和后续观察；未解验收疑问仍禁止 pass/fail。
- 未测试/无法判断目标经封包、复核、报告仍完整保留。
- 新指南实际进入编译包、安装包，链接与指纹有效。
- 图片生成与产物一致，版本状态、日期和 Release 有据可查，公开产物不含真实项目资料。

这些检查不证明 AI 一定会主动询问，基线历史计数也不是 v0.1.5 验证结果。还需实际加载新版 Skill 做行为验收：

| 场景 | 应观察到的行为 |
| --- | --- |
| 缺低权限账号但验收明确 | 主动询问，依赖目标停止，不污染验收字段、不报通过或产品失败。 |
| 资料已提供并可安全核验 | 查证已有内容，不重复索取。 |
| 一个目标受阻，另一个独立 | 明确影响范围，独立目标依已有授权继续。 |
| 取消、空答、部分回答 | 未解决部分继续暂停，不代答或默认同意。 |
| 用户补资源、执行中新依赖 | 核实后恢复相关目标，新缺口仍触发判断。 |
| 角色不符，及真实低权限越权 | 分开处理资源不匹配与有效产品违反，给出依据。 |
| 多 worker 缺同一资源 | 协调者合并提问，无覆盖和擅自业务重放。 |
| 资源齐备但共享对象 | 仍处理并发冲突，不把 Space 当隔离证据。 |

每个目标分别列四态和依据；真实 UI 结果留真实截图。文件审查、模拟问答、合成事务与真实业务验证分开标注，少量场景通过不承诺模型总体能力提升。真实环境操作、安装切换和新增资源按用户当次授权执行。

## 8. 实施与本轮边界

建议先完成入口、资源指南和现有记录闭环，再做演变页与图示，最后统一包内容、工程回归及本地行为验收。可按行为规范、文档图示、包与验证分块提交。这是开发建议，不是 Skill 的固定业务流程。

设计轮仅核对附件、源码、远端引用、Release 和官方参考，新增本设计文档；当时未修改功能或在用 Skill、未执行测试或发布操作。后续用户已授权按本方案开发，明确暂不覆盖当前安装、合并 main 或发布。

主要取舍是本版先复用工具，不新增结构化资源台账。它减少重复状态和格式成本，但资源充分性与问题合并仍依赖 AI 判断；本地行为验收是关键。若验收出现具体工具缺口，再据事实调整设计。
