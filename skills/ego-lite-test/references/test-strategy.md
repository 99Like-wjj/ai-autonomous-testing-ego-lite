# 测试策略：AI 主导，而不是固定工作流

## 从已有用例或新功能进入

已有用例输入时，保留依据与关键约束，检查缺失前提，不任意重写预期。只有新需求/新功能说明时，由 AI 从需求段落提取必须达成的验收目标，给每项目标标明来源，然后选择受影响的现有流程、角色、状态、边界和反向场景。无需用户先提供结构化用例或业务测试代码。

先核实目标版本是否已经部署、有可测试入口，以及允许的账号与数据范围。未部署、功能开关不可用或缺少环境时，保留生成计划，相关检查记 blocked；未尝试的依赖项可记 not_run，不能当作产品缺陷。

不要求用户逐项审批 AI 生成的检查。可以直接进行范围内低风险规划与获授权测试；只有实质性规则歧义、来源冲突、关键前提不明或权限不足才询问。普通策略选择由 AI 自主完成。

行动前固定拟执行检查与关键条件，保留目标到来源段落的映射。探索过程中新增的检查另记增补版本及原因，报告时与初始必需目标分开；不能先观察 UI，再把实际行为改写成原本预期。helpers 的 start 只接收 AI 准备好的规范化 cases 文件，不生成用例或调用模型。

若已获得工具包仓库的绝对根目录，可从该根目录读取 examples/project.example/feature-request.md，了解新功能输入示意；不是从安装 Skill 目录解析此路径。示例不是能力基准或实测结果，不读取它也不影响测试。

## 固定任务含义，允许执行策略调整

从用户请求和可信项目资料形成简短任务约定。资料格式自由，Markdown、说明书或对话均可；JSON 只是可选交换格式，不强制把项目转成测试平台配置。

约定至少能回答：

- 测什么环境、目标功能、版本，以及本次不测什么？
- 必须满足哪些业务目标，依据具体来自哪里？
- 哪些输入、账号角色、租户、对象、初始状态和访问路径不可变？
- 允许哪些副作用、测试数据范围、读取方式与清理动作？
- 何时停止：目标已逐项核验、权限/前提阻塞、资源限制或用户要求？

例如要求“读者角色经列表进入条目详情，验证无编辑入口”，不能改成管理员直接访问详情、删掉待测条目或调用写 API 来让页面呈现预期状态。若只是到达页面的非关键导航失败，可以换等价导航；若路径本身是要求，绕过只能作为另一个诊断实验，原检查仍未完成。

新增证据可以改变测试顺序、观察手段和待查假设，不能暗中改变验收标准。用户明确修改要求后，保存新旧约定和变化原因，分开记录前后结果。

## 依据分层

| kind | 含义 | 可作出的结论 |
| --- | --- | --- |
| explicit | 用户或授权需求文档明确规定 | 有充分证据时，可判该要求满足或违反 |
| interpretation | 由字段、邻近规则或常见行为推断 | 仅报告“按此解释”的观察与待确认问题 |
| hypothesis | 为发现问题而提出的探索 | 报告现象与风险假设，不宣称违反已确认要求 |

为依据保留 source、原意及版本/日期（若有）。UI 当前行为、历史测试结论、Agent 的常识都不能自动成为业务规范。相互冲突的明确来源不能自行选一个更易通过的版本。

## 选择高价值检查

根据产品与风险选取正向、反向、边界、角色权限、状态迁移、持久化和重复提交等检查，不要求每个页面跑同一清单。先覆盖用户明确目标，再做授权范围内的探索。少量高证据检查优于大量未核实的“通过”。

测试前验证初始状态，而非假定配置已落实：目标环境是否正确、账号实际角色是否匹配、对象是否存在且属于本次测试范围、初始业务状态是否满足条件。无法验证时说明缺口；不能把错误 fixture 导致的拒绝归咎产品。

边界值应从明确规则推导。未知规则可以提出问题或作为 hypothesis 探索，不能编造限制后据此报 bug。若测试需要新建/删除数据，先核对授权和共享后端影响。

## 可选 cases 文件

在用户提供或确认的工具包仓库绝对根目录下，examples/cases.example.json 是虚构项目输入示意（非本 Skill 的安装依赖），不是能力验收集、基准分数集或固定业务测试套件。用户可完全不使用它，直接提供文档。

若使用文件助手，case 的 id 稳定且唯一；basis.kind 只能为 explicit、interpretation、hypothesis。criticalConditions 描述必须核验的前提；requiredPath 为 null 表示未指定必须路径，不表示可以绕过权限或伪造结果。expected 是可观察结果，不是操作指令清单。
