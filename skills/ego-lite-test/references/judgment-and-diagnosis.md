# 判断与归因

## 先判断证据，再判断结果

新功能是否已经部署、功能开关是否开启，应作为环境前提核验；未就绪导致的不可测试应记 blocked，而非产品失败。后端副作用只在实际可用、获授权的证据范围内判断：页面没有显示变化不证明后端没有写入；没有后端观察能力时披露限制，不猜测数据库结果。

一次检查至少对齐：需求依据 → 实际身份与前置状态 → 实际执行动作 → 可观察后果。需要保存后的持久化、下游权限或异步完成时，必须取得对应证据；单张成功提示截图、HTTP 200、network idle、工具零错误、执行者自报完成都不足以替代它。

若依据不明确、观察窗口不足、关键证据缺失或相互矛盾，保留不确定性。不要因为模型很自信或多个模型一致就补齐缺失事实。可由当前会话完成首轮审阅；如使用另一个审阅上下文，先提供冻结要求和原始脱敏证据，而不是只提供执行者结论。它仍不是独立真值或保证正确的裁判。

## 状态与原因分开

- pass：该检查的可观察预期有充分证据支持。对于 interpretation/hypothesis，必须写成“按解释满足”或“本次探索未见异常”，不是已确认产品验收通过。
- fail：有效执行且充分证据显示所记录预期不满足。推断性依据仍保留标签；fail 不是自动确诊产品 bug。
- inconclusive：尝试过但证据或规则不足以判定，包括未知写入结果、观察冲突、无法确定初始状态。
- blocked：已知外部障碍阻止检查，例如缺少授权、登录过期、目标环境不可达；解释具体障碍。
- not_run：尚未尝试，例如被前项阻塞、超出本轮范围或达到用户给定预算。

同时记录归因含义：产品嫌疑、Agent 操作错误、环境/数据问题、规则歧义或证据不足/未知。原因分类由 AI 依据证据判断，不由状态或报错字符串机械推出。若使用助手，将这些含义映射到工具包当前接口允许的 cause 值，在 rationale 中保留细节，不自行添加枚举。对执行错误无法检验产品预期时，用 inconclusive/blocked，而非拿 Agent 操作错误的 fail 充当产品失败。

## 产品异常的证据门槛

提出产品缺陷嫌疑前，检查明确规则、实际角色/租户、初始数据、动作目标与输入、后果是否均可核验；记录是否可安全复现及是否存在其他解释。满足这些条件可以给出更强证据，但不要把未查证的后端根因说成事实。不能安全复现时，保留首次证据及限制，不为“确认 bug”扩大风险。

诊断可沿证据选择下一项：重新观察当前页面、检查允许读取的持久化状态、核对真实身份、检查已授权且已采集的错误/网络信息、在独立授权 fixture 上补测。不是必须执行的固定排查 DAG，也不允许绕过被测 UI 路径，用后台写操作替 UI 完成业务。

## 首次失败与补测

保留首个失败/异常、当时前提、证据与时间。每次补测另记 attempt、动机、前提变化和结果；修正 Agent 定位、改变输入、重置数据或更换角色后通过，不得覆盖原记录。只有原约束未改变的补测才可讨论同一条件下的复现稳定性。

写入超时或连接断开时，先使用已授权只读观察核对对象、唯一标识和业务状态。确认未生效且仍获授权，才考虑重试；确认已生效则继续核验后果；无法分辨则停止该写入链，记 inconclusive 并请求必要帮助。禁止用反复点击、重复提交或清空状态来猜测结果。
