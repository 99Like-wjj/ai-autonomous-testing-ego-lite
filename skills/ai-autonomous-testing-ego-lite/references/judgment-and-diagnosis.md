# 判断与归因

## 先判断目标结果，再描述原因

目标结果只有 verified（已验证）、violation（发现违反）、inconclusive（无法判断）、not_tested（未测试）。AI 对冻结目标作判断，工具只校验结构、必要语义引用、证据关联和澄清限制。

- 已验证：目标所需前提与必要语义已观察，可观察预期有充分支持。点击成功、HTTP 200、按钮 enabled、助手自报完成都不能代替业务结果及必要持久化读回。
- 发现违反：依据明确，有效执行或有效状态观察足以证明目标预期不满足。可以同时记录根因未知；无需为所有 UI 违反查明后端原因。
- 无法判断：已经观察该目标，但前提、动作有效性、规则、结果或证据冲突仍阻止判断。指出缺的是什么，而不是笼统写“原因未知”。
- 未测试：该目标未开展检查，说明用户暂缓、资源未具备或其他实际原因。没有 assessment 只说明记录缺失，不能据此自动填未测试。

interpretation/hypothesis 的结果保留来源标签，不冒称已确认需求验收。某目标 clarificationQuestions 非空时，final 与 attempt 都不得 verified/violation；澄清后保留旧基线并创建有 followUpOf 关联的新目标。

## 观察与诊断分开入账

observations 记录事实、coveredRefs 和 evidenceIds；assessments 记录目标、四态、rationale、observationIds、gaps。diagnosis 可选，state 为 unknown/hypothesis/confirmed，category 为 product/agent/environment/spec/unknown。诊断文字与支持证据说明归因能确认到哪一层，不从业务状态或报错字符串自动推出。

一个前提已核验不等于整个目标已验证；页面旧值不证明后端从未写入。相反，UI 反馈本身违反明确要求时，后来保存成功也不能抹掉该违反。对未知后端副作用只披露实际证据范围，不猜数据库状态。

## 有区分力的正反例

**重命名：** 若同一对象、合法输入、产品支持的保存动作和独立读回都有可靠记录，读回仍是旧标题，且观察时机足以判断明确预期，可记 violation，diagnosis.state 为 unknown。没有后台根因不是降为无法判断的理由。

若只看到填写新标题后的弹窗截图，没有证据确认保存动作针对正确控件，或补试使用了尚未确认支持的 Enter 提交，则不能当作同条件复现。先保留当前观察与具体缺口，选择安全的只读核对；工具调用完成本身不补齐缺失事实。

**拖动：** 时间条未变可能是动作未触发、应用拒绝、回滚或业务处理异常。记录实际命中、动作与页面反馈，按需查看已有请求/错误和读回。不能仅凭“mouse 调用无错”判违反，也不能要求所有拖动检查都必须查数据库。缺口是否妨碍该目标判断由 AI 结合预期确定。

**上下文与下载：** 助手说“不知道”不能证明请求未携带上下文；下载事件超时不能证明文件未下载。按需取得能区分这些解释的观察；不要扩大原验收目标。方法见[执行经验](experience-execution.md)。

## 首次异常、补测与恢复

保留首次异常、前提、证据和已知时间；补测追加新条目并说明前提差异。改变定位、输入、角色或提交方式后取得结果，不覆盖旧记录，也不称为同条件复现。

未知写入先用授权内只读方式核对同一对象。确认未生效且仍获授权后再自主决定是否补试；已生效继续核验；仍未知则停止该写入链并说明缺口。数据事务原请求取回回执不代表重做页面操作。

诊断不是固定排查流程。AI 可重新观察页面、核对身份/对象、查询已授权且已采集的信息、使用独立合成数据补测，或保留无法判断。不可绕过必要 UI 路径用后台写操作完成业务，也不可为确认缺陷扩大权限。
