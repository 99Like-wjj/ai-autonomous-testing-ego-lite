# 测试策略：AI 主导，而不是固定工作流

## 两种来源，同等覆盖新功能与回归

按 [用例接收与生成](case-authoring.md) 接收外部用例或从需求生成用例。两者均可用于新功能与回归，统一采用 schemaVersion 8 的业务 goals、有序步骤、必要语义引用和顺序策略。保留来源与关键条件，不任意重写外部输入，不把模型推断当成明确规则。

仅生成时不要求部署或浏览器。执行前核实版本、入口、身份、数据与授权；未就绪则说明受影响范围，不当作产品缺陷。只询问实质性规则、资源或授权缺口，不要求用户逐项审批用例。

两类来源都在执行前校验、冻结。后加探索另记增补及原因，不能先观察 UI 再改写原本预期。本地工具只接收准备好的 cases 文件，不生成用例或调用模型；默认报告交付及资源确认见本地工具箱指南。

业务步骤表达意图和必要输入，AI 依据当前页面选择具体方法。验收要求只放在有来源的 goals，步骤与前提通过 requiredRefs 保留必要语义。不要将点击、条件和路径机械计为独立目标，也不要用过大的目标合并互不依赖的身份或数据条件。

每个 goal 保留 basis 和 expected；验收细节未定写 goal.clarificationQuestions，非空时该目标 final/attempt 不能 verified/violation。可独立判断的其他目标继续保留，澄清后新建修订基线并用 followUpOf 关联原目标。

实际行为与证据进入 observations，显式目标结论进入 assessments，串并行使用统一 entries。计划步骤不是执行证据，根因未知不是自动无法判断，缺少评估不是未测试；判断细节见[判断与归因](judgment-and-diagnosis.md)。

## 根据目标识别资源缺口

理解当前整轮目标和前提时按[资源充分性指南](resource-readiness.md)区分验收规则、资源可用性和操作授权。初期已知实质缺口尽早实际提问，用例细化时补入新依赖；不能只记为前提或阻塞。首次开始或恢复实际测试前，说明已知条件、剩余缺口和允许继续范围。暂停依赖动作，独立且条件充分、已授权的目标可继续，但不因此推迟其他已知缺口的沟通。

只设计或离线准备可交付带前提草案，不强求执行资源、不假称能执行。转回实际测试时回读同一资源依据及问答，按变化复查适用性；环境恢复不能替代其他条件。答复仅更新明确覆盖部分，未答和明确暂缓分别保留；补资源只有在原冻结条件保持时才不需修订基线。收尾对照原目标及实际问答，保留未完成范围与原因。

## 固定任务含义，允许执行策略调整

从用户请求和可信项目资料形成简短任务约定。资料格式自由，Markdown、说明书或对话均可；输入材料不必由用户手写 JSON；模型将用例整理为统一 schemaVersion 8 交换格式，不要求建立测试平台或编写业务代码。

约定至少能回答：

- 测什么环境、目标功能、版本，以及本次不测什么？
- 必须满足哪些业务目标，依据具体来自哪里？
- 哪些输入、账号角色、租户、对象、初始状态和访问路径不可变？
- 允许哪些副作用、测试数据范围、读取方式与清理动作？
- 何时停止：目标已逐项核验、权限/前提阻塞、资源限制或用户要求？

例如要求“读者角色经列表进入条目详情，验证无编辑入口”，不能改成管理员直接访问详情、删掉待测条目或调用写 API 来让页面呈现预期状态。若只是到达页面的非关键导航失败，可以换等价导航；若路径本身是要求，绕过只能作为另一个诊断实验，原检查仍未完成。

新增证据可在 stepOrder 许可范围内调整方法、观察手段和待查假设：strict 保持业务步骤顺序；adaptive 也不得破坏依赖或跳过步骤。不能暗中改变验收标准。用户明确修改要求后，保存新旧约定和变化原因，分开记录前后结果。

## 依据分层

| kind | 含义 | 可作出的结论 |
| --- | --- | --- |
| explicit | 用户或授权需求文档明确规定 | 有充分证据时，可判该要求满足或违反 |
| interpretation | 由字段、邻近规则或常见行为推断 | 仅报告“按此解释”的观察与待确认问题 |
| hypothesis | 为发现问题而提出的探索 | 报告现象与风险假设，不宣称违反已确认要求 |

为依据保留 source、原意及版本/日期（若有）。UI 当前行为、历史测试结论、Agent 的常识都不能自动成为业务规范。相互冲突的明确来源不能自行选一个更易通过的版本。

## 选择高价值检查

根据产品与风险选取正向、反向、边界、角色权限、状态迁移、持久化和重复提交等检查，不要求每个页面跑同一清单。先覆盖用户明确目标，再做授权范围内的探索。少量高证据检查优于大量未核实的“通过”。

测试前验证初始状态，而非假定配置已落实：目标环境是否正确、账号实际角色是否匹配、对象是否存在且属于本次测试范围、初始业务状态是否满足条件。无法验证时说明缺口；不能把错误 fixture 导致的拒绝归咎产品。

边界值应从明确规则推导。未知规则可以提出问题或作为 hypothesis 探索，不能编造限制后据此报 bug。若测试需要新建/删除数据，先核对授权和共享后端影响。

## 标准用例文件

两类来源采用 [用例接收与生成](case-authoring.md) 定义的同一格式。JSON 是交换记录，不是业务脚本或能力基准；用户可提供文档，由模型生成符合契约的用例。criticalConditions 是必须核验的前提，requiredPath=null 不代表可以绕过权限。各 goal 的 expected 与必要步骤分开保留，冻结前核对每个预期都有对应前提、动作和观察方式。真实用例始终放在私有工作区。

## 风险取舍与复测经验

优先考虑损失、影响对象、共享依赖及难观察的失败，不把未知概率写成精确分数。说明重要取舍和未覆盖，不承诺泛化覆盖率。修复后保留首次结果、版本与条件，复测原缺陷并选择受影响邻近行为；不默认全站重跑。设计方法见 [设计经验](case-design-guide.md)。
